# 認証・認可フロー あんちょこ（16日用）

各フローは「誰が、何を、どこへ送るか」で覚える。最後の「確認テスト」で、これまで間違えた所を自分で説明できるか確かめる。

## 0. 登場人物の呼び方

| 方式             | 利用者の端末          | ログインさせる側（IDを持つ）                                                                        | ログインを使う側（サービス）              |
| -------------- | --------------- | -------------------------------------------------------------------------------------- | --------------------------- |
| OAuth 2.0      | ブラウザ（ユーザエージェント） | 認可サーバ                                                                                  | クライアント（トークンでリソースサーバのAPIを呼ぶ） |
| OpenID Connect | ブラウザ            | OP（OpenID Provider）                                                                    | RP（Relying Party）           |
| SAML           | ブラウザ            | IdP（Identity Provider）                                                                 | SP（Service Provider）        |
| Kerberos       | クライアント（プリンシパル）  | KDC（Key Distribution Center） : AS（Authentication Server） と TGS（Ticket Granting Server） | サービス（サーバ）                   |
| WebAuthn       | ブラウザ＋認証器        | （認証器が鍵を持つ）                                                                             | RP（Webサイト）                  |

- OAuth 2.0は「認可（APIを使う権限の委譲）」の仕組み。認証（誰か）を扱うのがOpenID Connect（IDトークン）。

## 1. OAuth 2.0 認可コードグラント＋PKCE＋state

```
(1) クライアント → ブラウザ：302で認可サーバへ
    Location: https://auth.example/authorize?response_type=code&client_id=abcd1234
      &redirect_uri=https://app.example/callback&state=Xk29fQ7a
      &code_challenge=E9Melhoa...&code_challenge_method=S256
(2) 利用者が認可サーバでログインし、同意する
(3) 認可サーバ → ブラウザ：302でクライアントへ（認可コードをクエリで渡す）
    Location: https://app.example/callback?code=5810f68a...&state=Xk29fQ7a
(4) クライアント → 認可サーバ（ブラウザを通らない）：トークン要求
    POST /token
    Authorization: Basic （client_id:client_secret をbase64）
    grant_type=authorization_code&code=5810f68a...&redirect_uri=...&code_verifier=dBjftJeZ...
(5) 認可サーバ → クライアント：アクセストークン（JSON、Cache-Control: no-store）
(6) クライアント → リソースサーバ：Authorization: Bearer （アクセストークン）
```

| 要素 | 誰が作る | どこで使う | 防ぐもの |
|---|---|---|---|
| state | クライアント（利用者のセッションに紐付け） | (1)で送り、(3)で戻った値をセッションと照合 | CSRF（攻撃者の認可コードを被害者に使わせる攻撃） |
| code_verifier（検証コード） | クライアント（乱数） | (4)のトークン要求で送る | 認可コードの横取り |
| code_challenge（チャレンジコード） | クライアント（検証コードのSHA-256をbase64url化） | (1)の認可要求で送る。認可サーバが保管 | 同上（認可サーバが(4)で計算して照合） |
| client_secret | 認可サーバが発行 | (4)のクライアント認証 | クライアントのなりすまし（公開クライアントは持てない→PKCE） |
| 認可コード（code） | 認可サーバ | (3)で受け取り(4)で交換。短寿命・一度きり | ― |

- R5春Ⅱ問2で失点した点：攻撃者が入手した「エンコード値」は client_id:client_secret のbase64で、認可コードではない。トークン要求には認可サーバが発行した認可コード（code）が必要。
- 仕様で決まっている部分：パラメータ名（response_type、code、state、client_id、redirect_uri、grant_type、code_challenge、code_challenge_method、code_verifier）、値「code」「authorization_code」「S256」、Bearer（RFC 6749、6750、7636）。
- 任意の部分：エンドポイントのパス（/authorize、/token、/callback）、ドメイン名、各値。

## 2. OpenID Connect（IDトークンとnonce）

1. RPがnonceを生成し、利用者のセッションに保存する。
2. RP → ブラウザ → OP：認証要求（`scope=openid`、`nonce=…` を含む）。
3. OPが利用者を認証し、認可コードを返す（認可コードフローの場合）。
4. RPがトークン要求を送り、IDトークン（とアクセストークン）を受け取る。
5. RPがIDトークンを検証する：署名、iss（発行者がOPか）、aud（自分のclient_idか）、exp（期限内か）、nonce（1で保存した値と一致するか）。

- IDトークンはJWT（ヘッダ.ペイロード.署名）。sub が利用者の識別子。
- nonceが防ぐもの：IDトークンの再送（リプレイ）。stateが防ぐもの：CSRF。どちらもRPが生成し、要求に入れ、戻ってきた値を自分で照合する。
- 仕様で決まっている部分：scope「openid」、nonce、IDトークンのクレーム名（iss、sub、aud、exp、iat、nonce）（OpenID Connect Core 1.0）。

## 3. SAML（SP起点のSSO）

1. 利用者がSPにアクセスする。
2. SP → ブラウザ：302でIdPへ。SAMLRequest（AuthnRequest）をURLのクエリ文字列に入れる（HTTP-Redirectバインディング）。
   `Location: https://idp.example/sso?SAMLRequest=（圧縮→base64→URLエンコードした値）&RelayState=…`
3. IdPが利用者を認証する。
4. IdP → ブラウザ：SAMLResponse（IdPが署名したアサーション）を入れたフォームを返し、自動でSPにPOSTさせる（HTTP-POSTバインディング）。
5. SPがアサーションを検証する：IdPの署名、宛先（Audience、Recipient）、有効期限、InResponseTo（2の要求への応答か）。

- R4春Ⅱ問2で失点した点：SAMLRequestの格納場所はクエリ文字列（リダイレクト先URLに組み込まれるため）。
- 仕様で決まっている部分：パラメータ名「SAMLRequest」「SAMLResponse」「RelayState」、HTTP-Redirect／HTTP-POSTバインディング（SAML 2.0、OASIS）。
- 任意の部分：IdPのURL、各値。

## 4. Kerberos

```
(1) クライアント → AS（KDC）：AS-REQ（利用者のIDと、パスワード由来の鍵で暗号化した時刻）
(2) AS → クライアント：TGT（KDCの鍵で暗号化）
(3) クライアント → TGS（KDC）：TGS-REQ（TGT ＋ 使いたいサービス名）
(4) TGS → クライアント：ST（サービスの鍵で暗号化したサービスチケット）
(5) クライアント → サービス：AP-REQ（ST）
```

- STを受け取って検証するのはサービス側。KDC（認証サーバ）にはSTは送られない（R4春Ⅱ問2で失点した点）。
- サービスはSTを自分の鍵で復号して確認するので、(5)の時点ではKDCに問い合わせない。そのため、サービスの鍵で偽造したST（シルバーチケット）はKDCのログに残らない。
- 攻撃の型：
  - Kerberoasting：サービスアカウントのSTを取得し、オフラインでパスワードを総当たりする。サーバへのログイン試行ではないので、ログイン失敗の記録が残らない（R4春Ⅱ問2で「オフライン」の要素が欠けて減点）。
  - ゴールデンチケット：KDCのアカウント（krbtgt）の鍵でTGTを偽造する。
- 仕様で決まっている部分：AS／TGS／TGT／STの役割、メッセージ名（RFC 4120）。ポートはTCP・UDP 88。

## 5. WebAuthn（FIDO2、パスキー）

登録
1. RPがチャレンジを送る。
2. 認証器が鍵ペアを作り、秘密鍵は認証器の中に残す。公開鍵とクレデンシャルIDをRPに登録する。

認証
1. RPがチャレンジ（乱数）を送る。
2. 利用者が認証器で本人確認（生体認証やPIN）をする。生体情報は端末の外に出ない。
3. 認証器が、clientDataJSON（チャレンジ、オリジン、種別を含む）のハッシュと authenticatorData（RP IDのハッシュ等）に、秘密鍵で署名する。
4. RPが、チャレンジとオリジンが正しいか、RP IDが一致するかを確認し、登録済みの公開鍵で署名を検証する。

- フィッシングに強い理由：オリジンが署名対象に含まれ、RPが検証する。偽サイトで認証させても、オリジンが偽サイトのものになるので検証に失敗する（R5秋問3の論点。TLS証明書の確認と混同して失点）。
- 仕様で決まっている部分：clientDataJSON の challenge・origin・type、RP ID、署名の対象（W3C Web Authentication）。
