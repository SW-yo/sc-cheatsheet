## 1. OAuth 2.0 認可コードグラント＋PKCE＋state

### 1.1 前提（R5春Ⅱ問2）

- OAuthの正式な役割名（RFC 6749 1.1）
    - リソースオーナー（resource owner）：会員
    - ユーザーエージェント（user-agent）：Webブラウザ
    - クライアント（client）：新日記サービスのWebサーバやスマホアプリ
        - 新日記Webサーバは、client_secret を安全に保持できる前提のコンフィデンシャルクライアント。
        - 要件2のスマホアプリは、アプリ内に秘密を安全に置けないパブリッククライアント。そのため、client_secret に代わる保護としてPKCEが必要になる。
    - 認可サーバ（authorization server）：サービスTの認可サーバ
    - リソースサーバ（resource server）：サービスTのリソースサーバ
- client_idとredirect_uri
    1. W社が、サービスTに新日記サービスをクライアントとして登録する。このとき redirect_uri（https://△△△.com/callback）なども届け出る。
    2. 認可サーバが client_id（abcd1234）と client_secret を発行する。
    3. W社はそれを新日記Webサーバの設定に保持する。この問題では、環境変数に置いていたことが漏えいの原因になった。
    4. 以後のフローでは、新日記Webサーバが(2)のLocationに自分の client_id を埋め込む。
- code：認可コード（authorization code）。認可サーバは、発行したcodeを次の情報と紐付けて記録している。
    - どの会員が同意したか
    - どのクライアント（client_id）に対するものか
    - どの redirect_uri へ返したか
    - どの範囲（scope）が許可されたか
- 説明用の設定
    - サービスTのドメイン：auth.service-t.example（認可サーバ）、api.service-t.example（リソースサーバ）
    - セッションCookie名、投稿APIのパス、トークン値、記事ID

### 1.3 PKCE（R5春Ⅱ問2 図4、R4春Ⅱ問2 設問4(4)）

![[07_R5春Ⅱ問2_図4.png]]

- 検証コードとチャレンジコード（RFC 7636）
    - 検証コードをcode_challenge_methodで指定された方法で変換する（"S256"ならSHA-256でハッシュ化、"plain"ならそのまま）。
    - 生成するのはクライアント。
    - 検証するのは認可サーバ。
    - 本文の場合、クライアントの役割がスマホアプリと新日記Webサーバに分かれている。
    - 本問で生成者は２通り考えられるが、設問4(2)で問われているのは検証方法だけなので、どちらの解釈でも解答は変わらない。
        1. アプリが生成し、チャレンジコードは(3)で、検証コードは(6)の認可コードと一緒にWebサーバに送り、そこから(7) で認可サーバへ渡す。
        2. Webサーバが生成し、チャレンジコードを(2)のリダイレクトURLに埋め込んで(3)で、検証コードは手元に保持して(7) で認可サーバへ渡す。

(3) 認可要求：スマホアプリ → サービスT認可サーバ

http

```http
GET /authorize?response_type=code&client_id=abcd1234&redirect_uri=...&
code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256 HTTP/1.1
Host: auth.service-t.example
```

- code_challenge : チャレンジコード（code_challenge_methodでハッシュ化）

(7) アクセストークン要求：新日記Webサーバ → サービスT認可サーバ

http

```http
POST /oauth/token HTTP/1.1

Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=5810f68a...&redirect_uri=...&

```

- code_verifier : 検証コード
- 照合（下線④、設問4(2)）：認可サーバが、(7)の検証コードをSHA-256でハッシュ化してbase64urlエンコードした値と、(3)のチャレンジコードが一致するか確認する。

## 2. OpenID Connect（IDトークンとnonce）

### 2.1 手順（R4春Ⅱ問2 図10の(1)〜(8)）

![[07_R4春Ⅱ問2_図10.png]]

1. (1) サービス要求：ブラウザ → RP。
2. (2) リダイレクト：RP → ブラウザ。RPがnonce（とstate）を生成して利用者のセッションに保存し、認証要求のURLに入れる。
3. (3) 認証要求：ブラウザ → OP（`scope=openid`、`nonce=…` を含む）。nonceを入れるのは認証要求（w＝認証要求）。
4. (4) ログイン処理：OPが利用者を認証する。
5. (5) リダイレクト：OP → ブラウザ。認可コードを渡す（認可コードフローの場合）。
6. (6) 認可コード：ブラウザ → RP。
7. (7) トークン要求：RP → OP（トークンエンドポイント）。OPが認可コードを検証する。
8. (8) トークン応答：OP → RP。IDトークン（とアクセストークン）を返す（u＝(8)）。
9. RPがIDトークンを検証する（R2秋Ⅱ問2 図2の d）：署名、iss（発行者がOPか）、aud（自分のclient_idか）、exp（期限内か）、nonce（(2)で保存した値と一致するか。x＝IDトークン）。

- IDトークンはJWT（ヘッダ.ペイロード.署名）。sub が利用者の識別子。ヘッダ、ペイロード、署名は、それぞれbase64urlでエンコードする（R4春Ⅱ問2 v＝イ）。署名はOPの秘密鍵で作成し、署名アルゴリズムはヘッダで指定する。
- nonceが防ぐもの：IDトークンの再送（リプレイ）。stateが防ぐもの：CSRF。どちらもRPが生成し、要求に入れ、戻ってきた値を自分で照合する。
- nonceは、インプリシットフローとハイブリッドフローで必須、認可コードフローでは任意（R4春Ⅱ問2の本文は「ハイブリッドフローを用いる場合」）。
- 留意点：R4春Ⅱ問2 設問5(4)では、nonceを入れる先は「認証要求」、照合する対象は「IDトークン」。「トークン」とだけ書くとアクセストークンも含まれるので、IDトークンと書く。
- 仕様で決まっている部分：scope「openid」、nonce、IDトークンのクレーム名（iss、sub、aud、exp、iat、nonce）（OpenID Connect Core 1.0）。

## 3. SAML（SP起点のSSO）

### 3.1 手順と電文（R4春Ⅱ問2 図8の(1)〜(8)）

![[07_R4春Ⅱ問2_図8.png]]

(1) サービス要求：XPC → SaaS（SP）。

処理1（SaaS）：IDaaSに認証を要求するSAML Request（AuthnRequestというXML文書）を生成し、エンコードする。エンコード結果とIDaaSのログイン画面のURLを組み合わせて、リダイレクト先URLを生成する。

(2) SAML Requestを含むリダイレクト：SaaS → XPC。SAML Request（DEFLATE圧縮＋Base64エンコード）をクエリに含めたIdPのログイン画面URLへリダイレクトさせる（HTTP-Redirectバインディング）。

http

```http
HTTP/1.1 302 Found
Location: https://idp.example.com/login?SAMLRequest=fZJNT8Mw...&RelayState=abc123
```

(3) SAML Requestを含むHTTPリクエスト：XPC → IDaaS（IdP）。XPCのWebブラウザは、そのURLへ自動でGETリクエストを送る。

http

```http
GET /login?SAMLRequest=fZJNT8Mw...&RelayState=abc123 HTTP/1.1
Host: idp.example.com
```

処理2（IDaaS）：(3)のHTTPリクエスト中のクエリ文字列（e＝ウ）からSAML Requestを取得する。信頼関係が構築されたSaaSからの認証要求であることを検証する。

(4) ログイン画面応答：IDaaS → XPC。

(5) 認証情報：XPC → IDaaS。利用者が認証情報（ユーザーID、パスワード）を入力して送信する。

処理3（IDaaS）：認証処理を行う。認証が成功した場合、IdPの秘密鍵（IdPのデジタル証明書の公開鍵と対になる鍵）でSAMLアサーションに署名し、署名を含むSAML Responseの送信フォームを生成する。

(6) SAML Responseの送信フォーム：IDaaS → XPC。

http

```http
HTTP/1.1 200 OK
Content-Type: text/html

<form method="post" action="https://sp.example.com/saml/acs">
<input type="hidden" name="SAMLResponse" value="PHNhbWxw...">
<input type="hidden" name="RelayState" value="abc123"> </form>
```

- ページ読込み時にスクリプトで自動送信する。
- value="PHNhbWxw..." : SAMLアサーションを含む「SAML Response」全体をBase64エンコードした値。

(7) SAML Response：XPC → SaaS。SAML Response（Base64エンコード、圧縮なし）をSPのACS URL（送信フォームの送信先）に自動送信する（HTTP-POSTバインディング）。

http

```http
POST /saml/acs HTTP/1.1
Host: sp.example.com
Content-Type: application/x-www-form-urlencoded

SAMLResponse=PHNhbWxw...&RelayState=abc123
```

処理4（SaaS）：SAML Responseに含まれるデジタル署名を、事前に共有してあるIdPのデジタル証明書で検証し、署名がIDaaSのもの（f＝ア）であること、及びSAMLアサーションの偽造（g）がないことを確認する。SAMLアサーションの内容を検証し、サービス提供すべきかどうかを決定する。

(8) サービス提供：SaaS → XPC。

### 3.2 処理4で確認するもの、事前共有するもの

- SAML Responseおよびその中のSAMLアサーションに記載の情報
    - 署名：アサーション（またはResponse）内のSignature要素（IdPのデジタル証明書で検証）
    - 宛先：Response要素のDestination属性と、アサーション内のRecipient属性（SPのACS URL）
    - 対象SP：アサーション内のConditions配下のAudience要素（SPのエンティティID）
    - 有効期限：アサーション内のConditionsのNotBefore・NotOnOrAfter属性
    - Requestとの対応：Response要素とアサーション内のInResponseTo属性
- SPとIdP間で事前共有する情報（R4春Ⅱ問2 h＝1、i・j＝3、4）
    - IdPのログイン画面URL（処理1で用いるURL）
    - SPのACS（Assertion Consumer Service）URL
    - IdPのデジタル証明書（処理3と処理4で必要）
    - SAMLアサーションで用いる属性
    - SP・IdPそれぞれの識別子（エンティティID）。信頼関係が構築された相手かの確認に使い、SAMLRequest（SP）とSAMLResponse（IdP、SP）に含まれる。

### 3.3 留意点

- R4春Ⅱ問2 設問3(1)：SAMLRequestの格納場所はクエリ文字列（e＝ウ）。処理1でリダイレクト先URLに組み込まれるため。
- R4春Ⅱ問2 設問3(3)：処理4で確認するのはアサーションの「偽造」がないこと。

- R3春Ⅱ問2 設問4(4)：管理していない機器からのサービス要求は、図3の5.〜6.（IDaaSでの認証）で遮断される。判定方法はTLSクライアント認証による検証。
- 仕様で決まっている部分：パラメータ名「SAMLRequest」「SAMLResponse」「RelayState」、HTTP-Redirectバインディング（圧縮、Base64、URLエンコードでクエリ文字列に入れる）、HTTP-POSTバインディング（Base64、圧縮なし）（SAML 2.0、OASIS）。

## 4. Kerberos

### 4.1 手順（R4春Ⅱ問2 図7）

![[07_R4春Ⅱ問2_図7.png]]

1. (1) XPC → 認証サーバ：利用者IDとパスワード（図7の表記）。RFC 4120ではAS-REQで、利用者のIDと、パスワード由来の鍵で暗号化した時刻を送る。
    - 処理1（認証サーバ）：利用者IDとパスワードが正しければ、TGTを発行する。
2. (2) 認証サーバ → XPC：TGT（AS-REP）。XPCがTGTを保存する。
    - TGTは、利用者のアクセス権限を示すチケット。TGT発行用アカウント（krbtgt）のパスワードハッシュ値を鍵として暗号化されている（図7の注1）。
3. (3) XPC → 認証サーバ：TGT（TGS-REQ。使いたいサービス名も送る）。利用者のGrWサーバへのアクセス要求を受けて送る。
    - 処理2（認証サーバ）：TGTを復号して検証し、問題なければSTを発行する。
4. (4) 認証サーバ → XPC：ST（TGS-REP）。XPCがSTを保存する。
    - STは、アクセス対象のサーバごとに発行されるチケット。サーバ管理者アカウントのパスワードハッシュ値を鍵として暗号化されている（図7の注2）。
5. (5) XPC → GrWサーバ：ST（AP-REQ）。
    - 処理3（GrWサーバ）：STを復号して検証し、問題なければアクセスを許可し、サービスを提供する。

### 4.3 留意点

- STを受け取って検証するのはサービス（GrWサーバ）側。KDC（認証サーバ）にはSTは送られない（R4春Ⅱ問2 設問2(1)、下線②。解答例「STは認証サーバに送られないから」）。
- サービスはSTを自分の鍵で復号して確認するので、(5)の時点ではKDCに問い合わせない。そのため、サービスの鍵で偽造したST（シルバーチケット）はKDCのログに残らない。
- 攻撃の型：
    - Kerberoasting：サービスアカウントのSTを取得し、オフラインでパスワードを総当たりする。サーバへのログイン試行ではないので、ログイン失敗の記録が残らず、アカウントロックも効かない（R4春Ⅱ問2 設問2(2)、下線③。解答例「総当たり攻撃はオフラインで行われ，ログインに失敗しないから」。「オフライン」の要素を必ず書く）。
    - ゴールデンチケット：KDCのアカウント（krbtgt）の鍵でTGTを偽造する。
- 仕様で決まっている部分：AS／TGS／TGT／STの役割、メッセージ名（RFC 4120）。ポートはTCP・UDP 88。

### 4.2 【補足】過去問の図との対応

R4春Ⅱ問2 図7（XPCからGrWサーバにアクセスする場合）と表1（処理1〜3）。図の「認証サーバ」がKDC（ASとTGS）に当たる。図7には番号がないため、矢印の順に(1)〜(5)を付けた（番号は説明用）。

## 5. WebAuthn（FIDO2、パスキー）

### 5.1 登録と認証（R5秋問3 図2）

![[07_R5秋問3_図2.png]]

図の記号と仕様の対応（説明用の対応づけ）：乱数c、c′＝チャレンジ、IDc＝クレデンシャルID、ドメイン＝RP ID、H(ドメイン)＝authenticatorData中のRP IDのハッシュ、H(オリジンb || 乱数c′)≒clientDataJSONのハッシュ、公開鍵K・秘密鍵K＝クレデンシャルの鍵ペア、公開鍵A・秘密鍵A・証明書A＝アテステーション用の鍵と証明書。

登録（H31春Ⅰ問2 図5。図に番号がないため、矢印の順に(1)〜(5)を付けた。番号は説明用）

1. (1) ブラウザ → 認証サーバ：オーセンティケータの登録要求。認証サーバが乱数cを生成する。
2. (2) 認証サーバ → ブラウザ：利用者ID、ドメイン、乱数c。RPがチャレンジを送る。
3. (3) ブラウザ → 認証器：利用者ID、ドメイン、H(オリジンb || 乱数c)。
    - 認証器：生体認証で利用者を確認し、IDcを発行する。IDcごとに鍵ペア（公開鍵K、秘密鍵K）を作り、秘密鍵は認証器の中に残す（IDc、利用者ID、ドメイン、公開鍵K、秘密鍵Kの組合せを登録）。秘密鍵A（c＝ウ）を用いて署名Lを生成する。
4. (4) 認証器 → ブラウザ：IDc、H(ドメイン)、公開鍵K、証明書A、署名L。
5. (5) ブラウザ → 認証サーバ：IDc、H(ドメイン)、公開鍵K、証明書A、オリジンb、乱数c、署名L。
    - 認証サーバ：オリジンbとオリジンsの一致、乱数cの一致を確認し、証明書Aを検証する。公開鍵A（d＝ア）を用いて署名Lを検証する。公開鍵とクレデンシャルID（利用者ID、IDc、公開鍵Kの組合せ）をRPに登録する。

認証（R3秋Ⅱ問1 図10の(1)〜(5)。H31春Ⅰ問2 図6も同じ流れ）

1. (1) ブラウザ → 認証サーバ：利用者ID。認証サーバは利用者IDに対するIDcを選択し、乱数c′を生成する。
2. (2) 認証サーバ → ブラウザ：IDc、ドメイン、乱数c′。RPがチャレンジ（乱数）を送る。
3. (3) ブラウザ → 認証器：利用者ID、IDc、ドメイン、H(オリジンb || 乱数c′)。オリジンbはブラウザが付ける。
    - 利用者が認証器で本人確認（生体認証やPIN）をする。生体情報は端末の外に出ない。
    - 認証器が、clientDataJSON（<mark style="background: #FFB8EBA6;">チャレンジ、オリジン</mark>、種別を含む）のハッシュと authenticatorData（RP IDのハッシュ等）に、秘密鍵で<mark style="background: #FFB8EBA6;">署名</mark>する。図では、秘密鍵K（H31春Ⅰ問2 e＝エ）を用いて、H(ドメイン)とH(オリジンb || 乱数c′)に対する署名Mを生成する。
4. (4) 認証器 → ブラウザ：IDc、H(ドメイン)、署名M。
5. (5) ブラウザ → 認証サーバ：IDc、H(ドメイン)、オリジンb、署名M（H31春Ⅰ問2 図6では乱数c′も送る）。
    - RPが、チャレンジとオリジンが正しいか、RP IDが一致するかを確認し、登録済みの公開鍵で署名を検証する。図では、オリジンbがKサービスのものであること（H31春Ⅰ問2 図6では、オリジンbとオリジンsの一致）を確認し、IDcに対する公開鍵K（f＝イ）を選択して署名Mを検証する。

- フィッシングに強い理由：<mark style="background: #FFB8EBA6;">オリジンが署名対象に含まれ</mark>、RPが検証する。偽サイトで認証させても、オリジンが偽サイトのものになるので検証に失敗する。
- 留意点：
    - R5秋問3 設問2(5)（図2の下線⑥）：解答例は「認証に用いる情報に含まれるオリジン及び署名をサーバが確認する仕組み」。TLSのサーバ証明書の確認とは別の仕組みなので、混同しない。
    - H31春Ⅰ問2 設問2(3)（下線④）：解答例は「認証サーバXでオリジンbとオリジンsの一致を確認しているから」。
    - R3秋Ⅱ問1 設問5(1)：(3)〜(5)でオリジンbを使うのは、攻撃者がメッセージをKサービスとの間で中継する（g）ことを防ぐため。
    - H31春Ⅰ問2 設問2(2)：登録の署名Lは秘密鍵A（c）で作り公開鍵A（d）で検証する。認証の署名Mは秘密鍵K（e）で作り公開鍵K（f）で検証する。
- 仕様で決まっている部分：clientDataJSON の challenge・origin・type、RP ID、署名の対象（W3C Web Authentication）。

### 5.2 パスキープロバイダ

パスキープロバイダの役割り（Google、Microsoft、Apple）

- RPと認証器は直接やり取りしない。間にブラウザやOSが入る（RP↔ブラウザはWebAuthn、ブラウザ↔認証器はCTAP2）。
- 認証器：Googleパスワードマネージャー、Windows Hello、iCloudキーチェーンなどが秘密鍵を保管し、署名する。RPが受け取るのは公開鍵と署名だけである。
- 同期：複数の端末で同じパスキーを使えるのは、提供者のクラウドが鍵をエンドツーエンド暗号化して同期するからである。
- 同期できるパスキーと端末に固定されたパスキーは、authenticatorDataのBEフラグ（同期できる）とBSフラグ（同期済み）でRPが区別できる。
- スマートフォンを別の端末の認証器として使う場合は、QRコードとBLEで端末が近くにあることを確かめる（ハイブリッド方式）。R3秋Ⅱ問1 図10は、スマートフォンをBluetooth経由で認証器として使う構成。
- 「Googleでログイン」はWebAuthnではなくOIDCである。利用先のサイトが受け取るのはIDトークンで、パスキーを使うのはGoogleが自社のログイン（Google＝RP）をするときだけである。
- TOTP（Microsoft Authenticatorなど）はRFC 6238の共有秘密方式で、WebAuthnとは別物である。パスキーを追加するときに既存のTOTPを求めるのは各サービスの運用で、仕様ではない。
- 仕様で決まっている部分：WebAuthn API（W3C）、CTAP2とハイブリッド方式（FIDO Alliance、CTAP 2.2）、BE/BSフラグ。
- 各社独自の部分：同期と回復の方式、OSのAPI（Android Credential Managerなど）。

### 5.3 呼称に関して

仕様の用語と業界の呼び名で、総称が分かれている。

- 仕様（WebAuthn、CTAP）の用語は「認証器（authenticator）」。端末に組み込まれたものは<mark style="background: #FFB8EBA6;">「プラットフォーム認証器」</mark>、USBキーのように持ち歩くものは<mark style="background: #FFB8EBA6;">「ローミング認証器」</mark>と呼ぶ。
- 仕様は同期の仕組みを定義しないため、同期型の提供者を指す専用の用語もない。
- 業界では「パスキープロバイダ（passkey provider）」が通称で、FIDO Allianceの解説や各社の文書で使われている。「パスワードマネージャー」と呼ばれることもある。
- OSのAPIでは「クレデンシャルプロバイダ（credential provider）」で、AndroidのCredential Managerや、AppleのCredential Provider Extensionで使われる。FIDO Allianceのパスキー移行仕様（Credential Exchange）も、この呼び方。
- 過去問では「オーセンティケータ」（H31春Ⅰ問2）、「FIDO認証器」「認証器」（R3秋Ⅱ問1）と表記されている。

3. TOTPアプリがカメラでQRコードを読み取り、ドメインと共通鍵を登録する。

認証（図4）

1. ブラウザ → 認証サーバ：認証要求（利用者ID、パスワード）。認証サーバが利用者IDとパスワードを検証する。
2. 認証サーバ → ブラウザ：OTP要求。
3. TOTPアプリが現在時刻と共通鍵からOTPを算出し、利用者がOTPをブラウザに入力する。
4. ブラウザ → 認証サーバ：OTP。認証サーバが利用者IDに対する共通鍵を選択し、現在時刻と共通鍵からOTPを検証する。
5. 認証サーバ → ブラウザ：利用者IDの認証結果。

- 留意点：
    - H31春Ⅰ問2 設問2(1)（下線③）：偽サイトは、OTPの入力を要求し、OTPを認証サーバXに中継する。OTPにはどのサイトに入力したかの情報が入らないので、リアルタイムの中継を防げない。
    - R5秋問3 設問2(1)（下線②）：解答例は「偽サイトに入力されたTOTPを入手し，そのTOTPが有効な間にログインした」。有効な間に正規サイトへ入力する、という要素を書く。
    - R2秋Ⅱ問2 設問1(1)(2)：QRコードに含まれ、OTPの生成に使う情報はシェアードシークレット。QRコードを第三者に読み取られると、第三者のOTPアプリで不正にOTPを生成される。
- 仕様で決まっている部分：TOTPの生成方式（RFC 6238）。QRコードの中身（otpauth://形式）はRFCではない。
