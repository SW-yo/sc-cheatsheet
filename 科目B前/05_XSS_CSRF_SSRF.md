# XSS・CSRF・SSRF あんちょこ（攻撃の流れ）

「過去問解答案」Excelのメモ（R6春問3_r1、R5秋問1、R5春Ⅱ問1、R4春Ⅱ問1）から、攻撃の流れの部分を抜き出して整理したもの。

## 0. 3つの違い（最初にここで仕分ける）

| | 誰の権限で | 何が動く／送られる | 攻撃者は応答を読めるか | 主な狙い |
|---|---|---|---|---|
| XSS | 被害者（ブラウザ） | 攻撃者のスクリプトが、正規サイトのオリジンで動く | 読める（スクリプトが読んで外に送る） | Cookie窃取、被害者権限での任意の操作、偽フォーム |
| CSRF | 被害者（ブラウザ） | 攻撃者が決め打ちした1つのリクエストが、被害者のCookie付きで送られる | 読めない（同一オリジンポリシー） | 登録情報の変更、送金、投稿など状態の変更 |
| SSRF | 脆弱なサーバ | サーバ自身が、攻撃者の指定した宛先へリクエストを送る | 読める（返る場合）／読めない（Blind SSRF） | 内部の管理画面、内部API、クラウドのメタデータ（IMDS） |

## 1. XSS（Cross-Site Scripting）

- Webアプリが利用者の入力をエスケープせずにHTMLへ出力することが原因。攻撃者のスクリプトが、被害者のブラウザ上で、そのサイトのオリジンの権限で実行される。
- スクリプトなので、Cookieを読む、画面を書き換える、条件分岐しながら複数のリクエストを送る、応答を読んで次の操作を決める、といった任意の動作ができる。

### 1.1 種類

| 種類 | 発火の仕方 | 誘導の要否 |
|---|---|---|
| 反射型 | リクエストの値がそのまま応答に出力される | 罠リンク・罠サイトで被害者に送らせる必要がある |
| 格納型（持続型） | 入力がDBなどに保存され、それを表示する別画面を見た人のブラウザで発火する | 不要。表示した人全員が対象 |
| DOM-based | クライアント側のJavaScriptがDOMに書き込むときに発生。サーバの応答には現れないこともある | 種類による |

### 1.2 格納型の流れ（R6春問3：問合せ機能 → 管理者の画面）

1. 攻撃者が問合せ機能で、Cookieを攻撃者のサイトへ送るスクリプトを格納する。
2. 管理者が問合せ管理機能で、その問合せを閲覧する。
3. スクリプトが管理者の権限で動き、管理者のCookie（SESSIONID）が攻撃者に届く（HttpOnly属性がないため読める）。
4. 攻撃者はそのCookieで会員管理機能にアクセスし、全会員の情報を取得する（セッションの有効期間内なら成立）。

- 入力した画面ではなく別画面に出力されるため、脆弱性診断ツールでは見つからず、設計書を調べた手動分析で発見された。

### 1.3 格納型の流れ（R5秋問1：字数制限の回避）

1. 攻撃者（会員A）が、50字制限を回避するためスクリプトを15件に分割して、レビュータイトル欄に投稿する。
2. 各投稿の末尾を「/*」、次の投稿の先頭を「*/」にして、投稿の間のHTML（</div>など）をコメントにする。
3. 新しい順に表示されるため、スクリプトの末尾から先に投稿する。
4. 別の会員がレビュー閲覧ページを開くと、アプリはDBの内容をそのままHTMLに埋め込んで返す。
5. 投稿の間がコメントになり、1つの長いスクリプトとして、その会員のブラウザでサイトのオリジンとして実行される。
6. スクリプトがトークンを取得し、document.cookie（セッションID）をアイコン画像（a.png）としてアップロードする。
7. 攻撃者がその会員のアイコン画像をダウンロードし、テキストとして開いてセッションIDを取り出す。
8. そのセッションIDで会員になりすまし、購入やカード情報設定などの機能を使う。

### 1.4 反射型の流れ（R5春Ⅱ問1：二つ先の確認画面で出力）

1. 攻撃者は罠サイトを用意し、入力画面1の送信先URLあてに、姓（または名）にスクリプトを入れたフォームを置く。
2. メールなどで利用者に罠サイトのリンクを踏ませる。
3. 罠サイトのJavaScriptが、利用者のブラウザからフォームを自動送信する。
4. 利用者のブラウザが正規サイトにスクリプト入りの値を送り、入力画面2が表示される（この時点ではまだ実行されない）。
5. 利用者が「次へ」を押す（または罠サイトが見えないiframeで次の遷移も自動送信させる）と、確認画面でエスケープされずに出力される。
6. スクリプトが利用者のブラウザで、正規サイトのオリジンとして実行される。

### 1.5 属性値からの抜け出し（R4春Ⅱ問1：meta要素の content 属性）

```html
<!-- 出力のひな形 -->
<meta property="og:url" content="https://（ホスト名）/confirm?【queryString】">

<!-- queryString = "><img src=1 onerror=alert(1)><" のとき（成立する） -->
<meta property="og:url" content="https://（ホスト名）/confirm?"><img src=1 onerror=alert(1)><"">
```

1. 先頭の「"」で content 属性の値を閉じる。
2. 「>」で meta タグを閉じる。
3. 続く `<img src=1 onerror=alert(1)>` が独立したタグになり、画像の読み込み失敗で onerror が実行される。

- 「"」を `&quot;` にエスケープしていれば、属性値は閉じずにただの文字になる。
- `<img src=1 onerror=...>` は script という文字列を含まないので、「script」を消すだけのフィルタをすり抜ける。innerHTMLで挿入した `<script>` は実行されないが、onerror は実行される。
- 仕様で決まっている部分：属性値は次の「"」で終わる、「>」でタグが終わる、onerror は読み込み失敗で動く（HTML Living Standard）、og:url（Open Graph）。
- 任意の部分：「src=1」「alert(1)」（実行確認用の定番）、パス「/confirm」。

### 1.6 対策（解答の型）

| 対策 | 位置付け |
|---|---|
| 出力時のエスケープ（`< > & " '` を文字参照に変換）。出力先（HTML本文、属性値、JavaScript内、URL）に応じた方式を使う | 根本的解決（IPA「安全なウェブサイトの作り方」）。入力時のサニタイジングは不正解になりやすい（R5秋問1、R7秋問1で失点） |
| CookieのHttpOnly属性 | Cookieは読めなくなるが、XSS自体は防げない。被害者権限でのリクエスト送信は可能 |
| CSP | 読み込み・実行してよい範囲を制限して被害を緩和 |
| 入力値検証 | 補助的な対策 |

## 2. CSRF（Cross-Site Request Forgery）

- ログイン中の利用者を罠ページに誘導し、利用者のブラウザから正規サイトへ意図しないリクエストを送らせる。
- ブラウザがCookieを自動で付けるため、サーバは本人の操作と区別できない。
- 成立条件：①被害者がログイン中、②Cookieだけでセッション管理している、③リクエストの中身を攻撃者が予測できる。

### 2.1 流れ（R6春問3：トークンと利用者の紐付けがない）

1. 攻撃者が自分のアカウントでログインし、自分の csrf_token を取得する（他人のトークンを盗む必要はない）。
2. そのトークンと書き換え内容を hidden に入れた自動送信フォームを、罠サイトに置く。
3. 詐欺メールなどで被害者を罠サイトに誘導する。
4. 被害者のブラウザが被害者のCookie付きで `POST /shop/editmember` を送り、被害者の会員情報が変更される。

- 診断結果の読み方：値が空・パラメータなしはエラー（存在チェックはある）が、別アカウントのトークンが通る（セッションとの紐付けを検証していない）。
- 攻撃者が自分で送っても、被害者のCookieは付かない。「被害者のブラウザから送らせる」ことが要点。

### 2.2 対策（解答の型）

| 対策 | 要点 |
|---|---|
| CSRFトークン | 推測困難な値をセッションと紐付けて発行し、フォームのhiddenに埋め込む。受信時にセッション側の値と一致するか確認する。存在チェックだけ、「どこかで発行されたトークンか」の確認だけでは不十分 |
| SameSite属性 | Strict：他サイトからは送らない。Lax：他サイトからのトップレベル遷移のGETだけ送る（POST、iframe、画像読み込みでは送らない）。None：常に送る（Secure必須） |
| 再認証、Origin／Refererの確認 | 重要な操作の前 |

- 「どのような処理を行う機能か、具体的に」と問われたら、処理の中身を書く：トークンの発行、HTMLへの埋め込み、セッションとの紐付け、受信時の検証（R4春Ⅱ問1で失点）。

## 3. SSRF（Server-Side Request Forgery）

- サーバが外部から指定されたURLへアクセスする機能を悪用し、サーバ自身に攻撃者の意図した宛先へリクエストを送らせる。
- 狙われる機能：URL指定での画像やコンテンツの取得、Webhook、URLプレビュー、PDF生成など。
- 狙われる宛先：内部の管理画面、内部API、localhost、クラウドのメタデータサービス（IMDS）。
- 代表例：AWSのIMDS（169.254.169.254）からIAMロールの一時認証情報を盗む手口（2019年のCapital One事件）。
  - IMDSv1：GETだけで取得できる。
  - IMDSv2：PUTでトークンを取得し、ヘッダに付けてアクセスする。GETしか送れない単純なSSRFへの対策になる。
- 複数回のリクエストは、その都度攻撃者が送る。curlなどで脆弱なサーバを直接たたくイメージ。

### 3.1 流れ（R6春問3：pageパラメータで取得先を指定できる）

- 前提：WebサーバYは、pageの値で指定されたサイトPのページを代わりに取得して表示する。pageの値を検証していない。CMSの管理画面は「VPN接続した管理者PCかVPC内から」に制限されているが、SSRFではリクエストがVPC内のWebサーバYから出るため、この制限をすり抜ける。
- 方法F（GET固定）：管理画面の表示（GET）はできるが、ログインはPOSTのみ許可なのでできない。
- 方式1（IMDSv1相当）：pageにIMDSのクレデンシャル情報を返すURLを指定するだけで、クレデンシャルが応答に返る。
- 方法G（メソッドとヘッダを任意に指定できる）では、方式2（IMDSv2相当）も次の手順で突破される。
  1. トークンを発行するURLにPUTを送り、トークンを入手する。
  2. クレデンシャル情報を返すURLに、トークンをリクエストヘッダに入れてアクセスする。

### 3.2 対策（解答の型）

| 対策 | 要点 |
|---|---|
| 宛先の許可リスト | スキームとホストを固定。本問では「pageの値がサイトPのURL以外ならエラーにする」。拒否リスト方式は、IPアドレスの別表記、リダイレクト、DNSリバインディングで回避されやすい |
| 内部アドレス宛ての拒否 | プライベート、ループバック、リンクローカルのアドレスを拒否する。判定は名前解決後のIPアドレスで行う |
| ネットワーク側の制限 | サーバからの送信先を制限する（egress制御） |
| メタデータの保護 | IMDSv2の強制、クレデンシャルの最小権限化 |

- セッションIDの変更などは無関係で不正解（R6春問3で失点）。
