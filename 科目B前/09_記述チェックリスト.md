# 記述問題チェックリスト（失点の約8割が記述）

「過去問解答案」で△×になった記述の原因を、解く前・書く前に確認する項目にしたもの。

## 1. 設問を読むとき

- [ ] 問われ方の型に丸をつける。
  - 「理由を述べよ」→「〜だから」で終える。
  - 「方法・手順を述べよ」→ 何をどうするかを順に書く。
  - 「具体的に述べよ」「どのような処理か」→ 処理の中身を書く。下線部の言い換えは不可（R4春Ⅱ問1：CSRF対策機能は「トークンの発行、埋め込み、セッションとの紐付け、検証」）。
  - 「タイミング」「いつ」→ 時点を書く。内容を書かない（R4秋Ⅱ問2）。
  - 「効果」「何が防げるか」→ 防げる被害まで書く。
- [ ] 目的が「被害拡大の防止」か「再発防止」かを区別する（R4秋Ⅰ問3）。
- [ ] 記入欄の記号と設問の対応を確かめる（R6秋問4のk・lで取り違え）。
- [ ] 「表の項番で答えよ」「〜の観点で」などの条件に線を引く（R5春Ⅰ問2）。

## 2. 書くとき

- [ ] 字数の上限を超えない。超過は0点（R5春Ⅰ問2、R4秋Ⅰ問2、R4秋Ⅱ問2で計26点）。
- [ ] 主語（誰が）、対象（何を）、条件（どの場合に）が入っているか。
- [ ] 問題文の言葉（機能名、サーバ名、項目名）をそのまま使う。言い換えると採点で拾われにくい。
- [ ] 対策を書くときは「その対策で何が防げるか」まで書く（R6秋問4、R6秋問1）。
- [ ] 対策は、問題文の環境で実現できるものにする。既存の仕組みで難しいものは減点されやすい（R6秋問1のRDP監視）。
- [ ] 攻撃シナリオでは、問題文に書かれた侵入口で止める対策を選ぶ（R7秋問4のUSBメモリ）。

## 3. 用語はIPAの言い方で書く

| 問われる場面 | 書く言葉 |
|---|---|
| リスク対応の選択肢 | 回避、低減、移転、保有（JIS Q 31000では「共有」「保有」などの表現もあるが、試験では問題文の用語に合わせる） |
| XSSの根本対策 | 出力時のエスケープ（入力時のサニタイジングは保険的対策） |
| SQLインジェクションの根本対策 | プレースホルダ（バインド機構）を使ってSQL文を組み立てる |
| SSRFの対策 | 宛先を許可リストに限定する |
| CSRFの対策 | セッションと紐付けた推測困難なトークンの検証 |
| 脆弱性診断の組合せ | ツール（静的・動的）と、仕様を理解した人による検査（R7秋問1） |

## 4. 本番の時間配分（150分で2問）

- 最初の5分：4問の設問をざっと見て選ぶ。HTML・JavaScriptの読解やWeb・インシデント・サプライチェーンを優先し、Javaのコード読解が中心の問題は避ける。
- 1問あたり70分以内。記述の見直しに最後の5分を残す。
