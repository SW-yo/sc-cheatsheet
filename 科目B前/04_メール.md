# メール あんちょこ

元の「メール.txt」からメール関連の項目を抜き出して整形したもの。内容は元のまま、誤字だけ直している。

## 1. 送信ドメイン認証の全体像

| 技術 | 何を認証するか | 見るドメイン | DNSに置くもの |
|---|---|---|---|
| SPF | 送信元IPアドレス | エンベロープFrom（Return-Path）のドメイン | TXTレコード（v=spf1） |
| DKIM | 署名ドメインと、署名対象（ヘッダと本文）の改ざんの有無 | DKIM-Signature の d= のドメイン | TXTレコード（セレクタ._domainkey.ドメイン、v=DKIM1） |
| DMARC | SPF・DKIMの結果と、ヘッダFromとの一致（アラインメント） | ヘッダFromのドメイン | TXTレコード（_dmarc.ドメイン、v=DMARC1） |

## 2. SPF（Sender Policy Framework）

メール送信元が詐称されていないことを確認するための技術。RFC 7208で規定。

1. 受信側のメールサーバが、SMTPセッションのエンベロープのMAIL FROMのドメイン（エンベロープFromの@以降）を使ってDNSを参照する（エンベロープFromが空の場合はHELO／EHLOのホスト名）。
2. そこに登録されているSPFレコード（TXTレコード）から、機構（送信を許可するIPアドレス、allなど）と、それぞれに付く限定子（+／-／~／?）を読み取り、送信元が詐称されていないかの判定結果を出す。
3. その結果を元に、受信サーバが受け入れるか（受信、拒否、迷惑メール扱いなど）を判断する。

- SPFレコード（TXTレコード）自体は送信元が準備し、DNSに登録しておく。
- SPFが確認するのはエンベロープFromのドメインであり、ヘッダFromの詐称対策にはDMARCが必要。

例
```
v=spf1 ip4:192.0.2.1 include:_spf.example.net ~all
```

| 要素 | 意味 |
|---|---|
| v | バージョン |
| ip4 ／ ip6 | 送信を許可するIPアドレス |
| include | 外部サービスのSPFを取り込む |
| all | 指定した機構以外すべて |
| 限定子 + | 認証する（成功） |
| 限定子 - | 認証しない（失敗）。-all は厳格に拒否 |
| 限定子 ~ | 認証しないが正当なメールかもしれない（緩めの失敗）。~all |
| 修飾子 redirect | 別ドメインのSPFを使う |
| 修飾子 exp | 失敗時の説明文 |

- 仕様で決まっている部分：「v=spf1」「ip4:」「include:」「all」と限定子の記号。
- 任意の部分：IPアドレス、include先のドメイン（元のテキストでは「include:_://google.com」と崩れていたため、説明用の架空ドメインに置き換えた）。

## 3. DKIM（DomainKeys Identified Mail）

メールに電子署名を付与し、送信元の詐称や本文の改ざんがないかを認証する技術。RFC 6376で規定。

1. 送信側のメールサーバは、本文からハッシュ値（bhタグ）を作り、それを含むメールのヘッダから秘密鍵で署名（bタグ）を作成し、DKIM-Signatureとしてヘッダフィールドに追加する。
2. 受信側のメールサーバは、DKIM-Signatureのs（セレクタ）タグとd（ドメイン）タグから決まるFQDN（セレクタ._domainkey.ドメイン）で、DNSに登録されたDKIMの公開鍵（pタグ）を取得する。
3. 本文のハッシュを計算してbhタグと比較し、hタグで指定されたヘッダ（およびb=を空にしたDKIM-Signatureヘッダ自身）のハッシュと公開鍵でbタグ（署名値）を検証して、改ざんがないことを確認する。

- 公開鍵（pタグ）を含むDKIMレコード（TXTレコード）は送信元が準備し、DNSに登録しておく。
- DKIMが保証するのは、d= のドメインの管理者が署名し、署名対象のヘッダと本文がその後改ざんされていない点。ヘッダFromの詐称対策にはDMARCが必要。

DNSに登録するDKIMレコードの例
```
v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...
```

| タグ | 意味 |
|---|---|
| v | バージョン |
| k | 鍵のアルゴリズム |
| p | 公開鍵 |

### 3.1 DKIM-Signature（メールのヘッダに付く署名）

```
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed; d=example.co.jp; s=2026; h=from:to:subject:date; bh=...; b=...
```

| タグ | 意味 |
|---|---|
| v | バージョン（「1」固定） |
| a | 署名アルゴリズム（例：rsa-sha256） |
| b | 署名値（Base64）。hのヘッダとDKIM-Signatureヘッダ自身（bは空、bhを含む）から計算 |
| bh | 正規化した本文のハッシュ値（Base64） |
| c | 【任意】正規化方式。「ヘッダ/本文」で指定。省略時は simple/simple。simple はわずかな変更でも検証失敗、relaxed は空白の連続やヘッダ名の大文字・小文字の違いなどを許容 |
| d | 署名したドメイン（公開鍵を探す先。DMARCでヘッダFromと比較） |
| h | 署名対象ヘッダの一覧（Fromは必須） |
| s | セレクタ（「s._domainkey.d」で公開鍵を探す） |

- dとsでDNS用FQDNが決まる（[sの文字列]._domainkey.[dの文字列]）。
- DKIMはメッセージ（ヘッダと本文）に対する署名なので、SMTPのやり取りで渡されるエンベロープは署名に含められない。
- 仕様で決まっている部分：タグ名、「_domainkey」、「rsa-sha256」「relaxed」「simple」。
- 任意の部分：d= のドメイン、セレクタ「2026」、h= に並べるヘッダの選択（Fromは必須）。

## 4. DMARC（Domain-based Message Authentication, Reporting, and Conformance）

- Authentication（認証）：SPF・DKIMの結果とアラインメントで判定。
- Reporting（報告）：rua・rufタグによるレポート。
- Conformance（適合）：p（ポリシー）タグによる、失敗時の処理の要求。

SPF（送信元IPの認証）とDKIM（署名ドメインの認証・改ざん検知）の結果を受けた動作を指定する。SPFまたはDKIMのどちらかが成功し、かつ成功した方のドメインがヘッダFromのドメインと一致（アラインメント）した場合に成功。DNSに登録しておくTXTレコードで、受信側のメールサーバは「_dmarc.ヘッダFromのドメイン名」で探しにいく。RFC 7489で規定。

例
```
v=DMARC1; p=quarantine; rua=mailto:dmarc-report@example.co.jp
```

| タグ | 意味 |
|---|---|
| v | バージョン |
| p | DMARCが失敗したメールの扱いの要求。none＝処理を求めない（監視のみ、通常どおり配送）、quarantine＝疑わしいものとして扱う（迷惑メールフォルダへの隔離など）、reject＝受信拒否を求める。実際の処理は受信サーバ側のポリシーによる |
| rua | 集約レポート（日次などの統計）の送信先 |
| ruf | 失敗レポート（個々のメールの情報）の送信先 |
| adkim ／ aspf | アラインメントのモード（r＝relaxed、s＝strict） |
| sp | サブドメイン向けのポリシー |
| pct | ポリシーを適用する割合 |

- 仕様で決まっている部分：タグ名、「_dmarc」、p の値（none／quarantine／reject）。
- 任意の部分：レポートの送信先アドレス。

### 4.1 アラインメント

「SPFやDKIMで認証されたドメイン」と「ヘッダFromのドメイン」が一致しているかどうかを示す概念。

- SPFが認証するのは、エンベロープFrom（Return-Path）のドメイン。
- DKIMが認証するのは、d= のドメイン。
- 受信者が見るのは、ヘッダFromのドメイン。

アラインメントが取れている例（3者とも bank.example）
```
From: support@bank.example              ← ヘッダFrom
Return-Path: <bounce@bank.example>      ← SPFで認証されたドメイン
DKIM-Signature: ... d=bank.example      ← DKIMで認証されたドメイン
```
- 任意の部分：「bank.example」「support」「bounce」。

## 5. エンベロープ

SMTPでサーバ同士がやり取りする配送用の情報。具体的には MAIL FROM（送信元）と RCPT TO（宛先）。

- メールそのもの（ヘッダと本文）には含まれず、SMTPの配送コマンドとしてやり取りされる。その代わり、受信側サーバが配送時にエンベロープの内容をヘッダに書き写す。
  - MAIL FROM は Return-Path
  - RCPT TO は Received の for 句など
- 「メールに付いてくる」のではなく、「受信サーバが残した記録をヘッダから読み取る」という形をとる。

## 6. 通信路と本文の暗号化

| 技術 | 区間・対象 | 要点 |
|---|---|---|
| SMTP over TLS（SMTPS、ポート465、暗黙的TLS） | 主にメールソフト（MUA）～送信元メールサーバ | 最初からTLSで接続する。RFC 8314。送信元メールサーバの証明書を用いる。メール自体は暗号化しないため、サーバ上では平文 |
| STARTTLS | 主に送信元メールサーバ～送信先メールサーバ | 平文で接続を開始し、EHLOの後にSTARTTLSコマンドでTLSに切り替える（ポート25、587など）。RFC 3207。接続を受ける側のサーバの証明書を用いる。相手が対応していなければ平文で送る「日和見的暗号化」。STARTTLS対応の表示を消して平文に誘導するダウングレード攻撃（STRIPTLS）があり、対策はMTA-STS（RFC 8461）やDANE |
| S/MIME | メール本文（エンドツーエンド） | 公開鍵暗号方式で電子メールの暗号化と電子署名を行う規格。本文は共通鍵暗号、共通鍵の受渡しは公開鍵暗号。公開鍵の正当性は認証局（CA）が発行するメールアドレスごとのX.509証明書で保証する。通信当事者同士で証明書を共有しておく必要がある。フォーマットはCMS |
| PGP（Pretty Good Privacy） | メール本文（エンドツーエンド） | Philip Zimmermannが開発。公開鍵暗号方式で暗号化・署名を行う。利用者同士が互いの公開鍵に署名しあう「Web of Trust（信頼の輪）」で信頼関係を作り、公開鍵の検証にはフィンガープリント（ハッシュ値）を使う。RFC 4880 |

## 7. OP25B（Outbound Port 25 Blocking）

- ISPの管理下で、動的に割り当てたIPアドレスのホストから、自プロバイダのメールサーバを経由せずに外部へ向かう宛先ポート25番のSMTPを遮断する設定。
- スパムメール送信の踏み台にされることを防止する。
- 代替として587番（サブミッションポート）を使う。

## 8. メールヘッダインジェクション

- Webサイトの問合せフォームなどの入力欄に改行コード（CRLF＝%0D%0Aなど）を混入させ、メールの宛先（To、Cc、Bcc）や件名などを書き換える攻撃。
- 解答の型：「入力値に改行コードが含まれていたらエラーにする」「宛先などをヘッダに直接組み立てず、専用のライブラリやAPIを使う」。
