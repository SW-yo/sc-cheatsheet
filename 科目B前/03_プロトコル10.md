# プロトコル これだけは10項目

選んだ基準：これまでの失点（FTPのパッシブ、SNMPのコミュニティ、SNI）と、インシデント・Web・無線LANの問題で前提知識として出やすいもの。DNSとHTTPは別ファイル、メール系は「メール」ファイルを参照。

## 2. TCPの3ウェイハンドシェイク

1. クライアント → サーバ：SYN
2. サーバ → クライアント：SYN+ACK
3. クライアント → サーバ：ACK
- <mark style="background: #FFB8EBA6;">着眼点：SYNだけ大量に送って3を返さないとサーバの待ち行列があふれる（SYNフラッド）→ SYN Cookie。</mark>
- 着眼点：通信の向きは「SYNを送った側が接続元」。FWのルールやログを読むときの基準になる。

## 3. FTP（アクティブとパッシブ）

| モード                                               | データコネクションを張る向き                          | FWで困ること                       |
| ------------------------------------------------- | --------------------------------------- | ----------------------------- |
| <mark style="background: #FFB8EBA6;">アクティブ</mark> | サーバ（送信元ポート20）→ クライアント（PORTコマンドで通知したポート） | 外から内への接続になり、クライアント側のFWで止まりやすい |
| <mark style="background: #FFB8EBA6;">パッシブ</mark>  | クライアント → サーバ（PASV応答で通知されたポート）           | サーバ側で多数の高位ポートを開ける必要がある        |

- 制御コネクションは常にクライアント → サーバの21番。
- <mark style="background: #FFB8EBA6;">認証情報もデータも平文 → SFTP（SSH）やFTPS（TLS）に置き換えるのが解答の型。</mark>
- 仕様で決まっている部分：PORT／PASVコマンド、21番と20番（RFC 959）。パッシブのデータポート番号はサーバが毎回決める（任意）。

## 4. SSH

- サーバ認証：初回接続でサーバの公開鍵（ホスト鍵）の<mark style="background: #FFB8EBA6;">フィンガープリント（ハッシュ値）</mark>を確認し、<mark style="background: #FFB8EBA6;">known_hosts に保存</mark>する。以後、鍵が変わると警告が出る（中間者攻撃の検知）。
- 利用者認証：パスワード認証か公開鍵認証。<mark style="background: #FFB8EBA6;">公開鍵認証では、利用者の公開鍵をサーバの authorized_keys に登録し、秘密鍵で署名して本人であることを示す。</mark>
- 着眼点：秘密鍵はパスフレーズで保護する。<mark style="background: #FFB8EBA6;">踏み台サーバや攻撃者は authorized_keys に自分の公開鍵を追記して永続化する。</mark>
- <mark style="background: #FFB8EBA6;">ポートフォワーディング：-L（ローカル）、-R（リモート）でトンネルを作れる。FWをすり抜けた通信経路として悪用される。</mark>

## 5. TLS（SNIと証明書の検証）

-<mark style="background: #FFB8EBA6;"> ClientHello にSNI（接続したいホスト名）が平文で入る。</mark>サーバはこれで証明書を選ぶ。
- クライアントが証明書で確認すること：
  1. <mark style="background: #FFB8EBA6;">信頼済みのルート証明書までチェーンがつながる（中間証明書を含む）。</mark>
  2. <mark style="background: #FFB8EBA6;">有効期限内で、失効していない（CRL、OCSP）。</mark>
  3. <mark style="background: #FFB8EBA6;">接続先のホスト名がSAN（サブジェクト代替名）に含まれる。</mark>CNはかつての方式。
- <mark style="background: #FFB8EBA6;">通信の中身を検査する装置（TLS中間者型プロキシ）を使う場合、装置が発行する証明書を信頼させるため、装置のプライベートCAのルート証明書を端末に登録する（R7春問3の論点）。</mark>
- 仕様で決まっている部分：SNI拡張（RFC 6066）、SANによるホスト名照合（RFC 6125、RFC 9525）、X.509の構造（RFC 5280）。

## 6. SNMP

- <mark style="background: #FFB8EBA6;">マネージャ（監視側）がエージェント（監視対象）に問い合わせる（UDP 161）。エージェントは異常を自発的にトラップで通知する（UDP 162）。</mark>
- <mark style="background: #FFB8EBA6;">管理情報はMIB</mark>（項目はOIDで識別）。
- <mark style="background: #FFB8EBA6;">v1／v2cの認証はコミュニティ名</mark>（平文のパスワード相当）。初期値の <mark style="background: #FFB8EBA6;">public</mark> のままだと情報を読まれる、書込み可能なら設定を変えられる。
	- public：読取り専用（GET系）のコミュニティ名として多くの機器で初期値になっているもの
	- private：読み書き可能（SET可能）のコミュニティ名として初期値になっていることが多いもの
- <mark style="background: #FFB8EBA6;">v3はユーザ単位の認証と暗号化（USM）に対応。</mark>解答の型は「SNMPv3を使う」「コミュニティ名を推測困難な値にし、アクセス元を限定する」。

## 7. RADIUSとIEEE 802.1X（無線LAN・有線LANの認証）
### 7.1 RADIUS

| 役割      | 802.1Xでの名前                                            | 例            |
| ------- | ----------------------------------------------------- | ------------ |
| 利用者の端末  | <mark style="background: #FFB8EBA6;">サプリカント</mark>    | PC、スマホ       |
| 中継する機器  | <mark style="background: #FFB8EBA6;">オーセンティケータ</mark> | 無線AP、LANスイッチ |
| 判定するサーバ | <mark style="background: #FFB8EBA6;">認証サーバ</mark>     | RADIUSサーバ    |
### 7.2 IEEE802.1x

| EAP方式         | サーバの認証 | 端末（利用者）の認証                                            |
| ------------- | ------ | ----------------------------------------------------- |
| EAP-TLS       | サーバ証明書 | <mark style="background: #FFB8EBA6;">クライアント証明書</mark> |
| PEAP／EAP-TTLS | サーバ証明書 | <mark style="background: #FFB8EBA6;">ID・パスワード</mark>  |
### 7.3 留意点
- <mark style="background: #FFB8EBA6;">着眼点：端末側でサーバ証明書を検証しないと、偽AP（悪魔の双子）がIDとパスワードを集められる。</mark>
- <mark style="background: #FFB8EBA6;">RADIUSはAP（またはスイッチ）とサーバ間で共有鍵（シークレット）を使う。</mark>

## 8. NTP

- UDP 123。全機器の時刻を合わせないと、複数のログを突き合わせた調査ができない（インシデント問題の定番の解答）。
- <mark style="background: #FFB8EBA6;">古い実装の monlist 機能は小さな要求で大きな応答を返すため、リフレクション攻撃の踏み台になる。</mark>

## 9. syslog

- <mark style="background: #FFB8EBA6;">機器やサーバのログを集約サーバに送る仕組み。</mark>従来はUDP 514（届いた確認がない、改ざん・盗聴に弱い）。
- <mark style="background: #FFB8EBA6;">解答の型：「ログを別サーバに転送して保管する（侵入者がローカルのログを消しても残る）」「時刻を同期する」「TLSで送る（TCP 6514）」。</mark>

## 10. DHCPとARP（同一LAN内の攻撃）

- DHCP：端末がブロードキャストで要求し、サーバがIPアドレス、デフォルトゲートウェイ、DNSサーバを配る。<mark style="background: #FFB8EBA6;">偽のDHCPサーバがゲートウェイやDNSを攻撃者に向けられる → スイッチのDHCPスヌーピング（「L2スイッチでDHCPスヌーピングを有効にし、正規DHCPサーバ側のポートだけを信頼ポートにする」）。</mark>
- ARP：IPアドレスからMACアドレスを調べる。<mark style="background: #FFB8EBA6;">偽のARP応答で通信を自分に向ける（ARPスプーフィング）→ 重要機器のMACアドレスの静的登録、スイッチのポートセキュリティ、通信の暗号化。</mark>
