# プロトコル これだけは10項目

選んだ基準：これまでの失点（FTPのパッシブ、SNMPのコミュニティ、SNI）と、インシデント・Web・無線LANの問題で前提知識として出やすいもの。DNSとHTTPは別ファイル、メール系は「メール」ファイルを参照。

## 1. ポート番号早見（ログ解析とFW設定の問題で使う）

| ポート | プロトコル | ひとこと |
|---|---|---|
| TCP 20 / 21 | FTP データ / 制御 | 20はアクティブモードのデータ用 |
| TCP 22 | SSH（SCP、SFTPも） | |
| TCP 23 | Telnet | 平文 |
| TCP 25 / 587 / 465 | SMTP / サブミッション / SMTPS | 25はサーバ間、587と465は利用者の送信用 |
| UDP・TCP 53 | DNS | ゾーン転送はTCP |
| UDP 67 / 68 | DHCP サーバ / クライアント | |
| TCP 80 / 443 | HTTP / HTTPS | |
| TCP 88 | Kerberos | |
| UDP 123 | NTP | |
| UDP 161 / 162 | SNMP 要求 / トラップ | |
| TCP 389 / 636 | LDAP / LDAPS | |
| TCP 445 | SMB | 横展開（ラテラルムーブメント）で出る |
| UDP 514 | syslog | TLS版はTCP 6514 |
| UDP 1812 / 1813 | RADIUS 認証 / アカウンティング | |
| TCP 3389 | RDP | 横展開で出る |

- 仕様で決まっている部分：上の番号はIANAが割り当てたウェルノウンポート。
- 実際の運用では変更できるので、問題文の設定値が優先する。

## 2. TCPの3ウェイハンドシェイク

1. クライアント → サーバ：SYN
2. サーバ → クライアント：SYN+ACK
3. クライアント → サーバ：ACK
- 着眼点：SYNだけ大量に送って3を返さないとサーバの待ち行列があふれる（SYNフラッド）→ SYN Cookie。
- 着眼点：通信の向きは「SYNを送った側が接続元」。FWのルールやログを読むときの基準になる。

## 3. FTP（アクティブとパッシブ）

| モード | データコネクションを張る向き | FWで困ること |
|---|---|---|
| アクティブ | サーバ（送信元ポート20）→ クライアント（PORTコマンドで通知したポート） | 外から内への接続になり、クライアント側のFWで止まりやすい |
| パッシブ | クライアント → サーバ（PASV応答で通知されたポート） | サーバ側で多数の高位ポートを開ける必要がある |

- 制御コネクションは常にクライアント → サーバの21番。
- 認証情報もデータも平文 → SFTP（SSH）やFTPS（TLS）に置き換えるのが解答の型。
- 仕様で決まっている部分：PORT／PASVコマンド、21番と20番（RFC 959）。パッシブのデータポート番号はサーバが毎回決める（任意）。
- 手元のExcel（R5春Ⅰ問2_r1）のメモに「22はデータコネクション」とあるが、標準のデータポートは20番。問題文に別の設定があったかを確認しておく。

## 4. SSH

- サーバ認証：初回接続でサーバの公開鍵（ホスト鍵）のフィンガープリントを確認し、known_hosts に保存する。以後、鍵が変わると警告が出る（中間者攻撃の検知）。
- 利用者認証：パスワード認証か公開鍵認証。公開鍵認証では、利用者の公開鍵をサーバの authorized_keys に登録し、秘密鍵で署名して本人であることを示す。
- 着眼点：秘密鍵はパスフレーズで保護する。踏み台サーバや攻撃者は authorized_keys に自分の公開鍵を追記して永続化する。
- ポートフォワーディング：-L（ローカル）、-R（リモート）でトンネルを作れる。FWをすり抜けた通信経路として悪用される。

## 5. TLS（SNIと証明書の検証）

- ClientHello にSNI（接続したいホスト名）が平文で入る。サーバはこれで証明書を選ぶ。
- クライアントが証明書で確認すること：
  1. 信頼済みのルート証明書までチェーンがつながる（中間証明書を含む）。
  2. 有効期限内で、失効していない（CRL、OCSP）。
  3. 接続先のホスト名がSAN（サブジェクト代替名）に含まれる。CNはかつての方式。
- 通信の中身を検査する装置（TLS中間者型プロキシ）を使う場合、装置が発行する証明書を信頼させるため、装置のプライベートCAのルート証明書を端末に登録する（R7春問3の論点）。
- 仕様で決まっている部分：SNI拡張（RFC 6066）、SANによるホスト名照合（RFC 6125、RFC 9525）、X.509の構造（RFC 5280）。

## 6. SNMP

- マネージャ（監視側）がエージェント（監視対象）に問い合わせる（UDP 161）。エージェントは異常を自発的にトラップで通知する（UDP 162）。
- 管理情報はMIB（項目はOIDで識別）。
- v1／v2cの認証はコミュニティ名（平文のパスワード相当）。初期値の public のままだと情報を読まれる、書込み可能なら設定を変えられる。
- v3はユーザ単位の認証と暗号化（USM）に対応。解答の型は「SNMPv3を使う」「コミュニティ名を推測困難な値にし、アクセス元を限定する」。

## 7. RADIUSとIEEE 802.1X（無線LAN・有線LANの認証）

| 役割 | 802.1Xでの名前 | 例 |
|---|---|---|
| 利用者の端末 | サプリカント | PC、スマホ |
| 中継する機器 | オーセンティケータ | 無線AP、LANスイッチ |
| 判定するサーバ | 認証サーバ | RADIUSサーバ |

| EAP方式 | サーバの認証 | 端末（利用者）の認証 |
|---|---|---|
| EAP-TLS | サーバ証明書 | クライアント証明書 |
| PEAP／EAP-TTLS | サーバ証明書 | ID・パスワード |

- 着眼点：端末側でサーバ証明書を検証しないと、偽AP（悪魔の双子）がIDとパスワードを集められる。
- RADIUSはAP（またはスイッチ）とサーバ間で共有鍵（シークレット）を使う。

## 8. NTP

- UDP 123。全機器の時刻を合わせないと、複数のログを突き合わせた調査ができない（インシデント問題の定番の解答）。
- 古い実装の monlist 機能は小さな要求で大きな応答を返すため、リフレクション攻撃の踏み台になる。

## 9. syslog

- 機器やサーバのログを集約サーバに送る仕組み。従来はUDP 514（届いた確認がない、改ざん・盗聴に弱い）。
- 解答の型：「ログを別サーバに転送して保管する（侵入者がローカルのログを消しても残る）」「時刻を同期する」「TLSで送る（TCP 6514）」。

## 10. DHCPとARP（同一LAN内の攻撃）

- DHCP：端末がブロードキャストで要求し、サーバがIPアドレス、デフォルトゲートウェイ、DNSサーバを配る。偽のDHCPサーバがゲートウェイやDNSを攻撃者に向けられる → スイッチのDHCPスヌーピング。
- ARP：IPアドレスからMACアドレスを調べる。偽のARP応答で通信を自分に向ける（ARPスプーフィング）→ 重要機器のMACアドレスの静的登録、スイッチのポートセキュリティ、通信の暗号化。
