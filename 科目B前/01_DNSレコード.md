# DNSレコード あんちょこ

## 0. まず押さえる全体像

| 役割                      | 何をするか                                                                               | 試験での着眼点                                                                                                                                                                                                                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| スタブリゾルバ                 | OSが持つhostsファイルと端末のDNSキャッシュを参照し、どちらにもなければ設定されたフルサービスリゾルバに再帰問合せを送り、返った答えを使う（自分では辿らない） | ① hostsファイルはDNSより優先される。マルウェアが書き換えると偽サイトへ誘導される<br>② 参照先DNSサーバはDHCPで配られることが多い。不正DHCPサーバやマルウェアが書き換えると、攻撃者のDNSを使わされる<br>③ <mark style="background: #FFB8EBA6;">ブラウザ単位でDoHを有効にすると社内DNSを経由せず、フィルタやログを迂回される</mark>                                                                                                                      |
| フルサービスリゾルバ（キャッシュDNSサーバ） | 再帰問合せを受け、キャッシュになければ権威サーバへ反復問合せして答えを集め、TTLの間キャッシュする                                  | ① <mark style="background: #FFB8EBA6;">キャッシュポイズニングの標的。</mark>偽の応答が一度入ると、そのリゾルバの利用者全員がTTLの間偽サイトへ誘導される<br>② <mark style="background: #FFB8EBA6;">外部からの再帰問合せを受け付けるとオープンリゾルバになり、DNSリフレクション攻撃の踏み台になる </mark>→ 再帰問合せを社内のアドレスからに限定<br>③ <mark style="background: #FFB8EBA6;">DNSSECの検証はここで行う</mark>                                     |
| 権威DNSサーバ（コンテンツサーバ）      | 自ゾーンの情報だけを答える。キャッシュも再帰問合せもしない                                                       | ① ゾーン転送（AXFR）を誰にでも許すと、内部ホスト名などゾーン全体が漏れる → セカンダリのIPアドレスに限定、TSIGで認証<br>② 再帰問合せ機能は無効にする。権威とキャッシュを同じサーバに同居させず分離するのが定石<br>③ <mark style="background: #FFB8EBA6;">レジストラのアカウントを乗っ取られるとNSを書き換えられ、ドメインごと奪われる</mark><br>④ 解約済みサービスへのCNAME／NSが残るとサブドメインテイクオーバー<br>⑤ <mark style="background: #FFB8EBA6;">DNSSECの署名側（鍵の管理、親ゾーンへのDS登録）</mark> |

- <mark style="background: #FFB8EBA6;">ゾーン：権威DNSサーバ（プライマリとセカンダリの組）が責任をもつ名前の範囲。</mark>下位の名前を別の権威サーバに任せることを委任といい、親ゾーンと子ゾーンに同一内容のNSレコードを置いて行う。
- 再帰問合せ：「最終的な答えを返して」という問合せ。スタブ→フルサービスリゾルバ。DNSヘッダのRDビットを1にして送る。
- 反復問合せ：「知っている範囲で答えて（知らなければ次の問合せ先を教えて）」という問合せ。フルサービスリゾルバ→各権威サーバ。
- フルサービスリゾルバの辿り方：キャッシュ → キャッシュ内で最も近い委任先 → 何もなければルート（ルートのアドレスはルートヒントとして設定に持つ）。
（仕様で決まっている部分：RDビット（RFC 1035）、AXFR（RFC 5936）、TSIG（RFC 8945）、プライミング問合せ（RFC 8109））

## 1. リソースレコードの書式

```
www.example.jp.   3600   IN   A   192.0.2.10
```

| 名前              | TTL  | クラス | タイプ | RDATA（値）   |
| --------------- | ---- | --- | --- | ---------- |
| www.example.jp. | 3600 | IN  | A   | 192.0.2.10 |

- 名前：そのレコードが<mark style="background: #FFB8EBA6;">「どの名前についての情報か」を示す欄（所有者名）</mark>。<mark style="background: #FFB8EBA6;">DNSの問合せは「名前＋タイプ」の組で行い</mark>、例えば「www.example.jp のA」「\_dmarc.example.jp のTXT」のように引く。example.jp、www.example.jp、\_dmarc.example.jp などはすべて別の名前として扱われ、それぞれに別のレコードとして置いておくことでDNSを機能させる（受信側などはこの名前を指定してDNSに問い合わせるので、名前が違うと見つけてもらえない）。
- 名前の末尾の「.」：ルートまで省略なしに書いた完全修飾名（FQDN）の意味。ゾーンファイルで「.」を付けないと、後ろにゾーン名が補われる。
  - 末尾に「.」あり：省略なしの完全な名前として扱われる。
  - 末尾に「.」なし：省略形として扱われ、後ろにゾーン名（ここでは example.jp.）が自動で付け足される。
```
; example.jp ゾーンのゾーンファイル内
www.example.jp.   IN A 192.0.2.10   ; → www.example.jp（意図どおり）
www               IN A 192.0.2.10   ; → www.example.jp（省略形。上と同じ意味）
www.example.jp    IN A 192.0.2.10   ; → www.example.jp.example.jp（誤り）
```
- TTL：キャッシュしてよい秒数。長いほど、レコードの変更も偽の応答も長く残る。切替作業の前に短くしておくと反映が早い。
- クラス：<mark style="background: #FFB8EBA6;">実務上は「IN」（Internet）しか使わない。</mark>そのレコードがどのネットワーク体系のものかを示す欄。
- タイプ：レコードの種類。「2. レコード早見表」に詳述。
- RDATA：Resource Dataの略で、レコードの値。<mark style="background: #FFB8EBA6;">中身の形式はタイプごとに決まっており</mark>、AならIPv4アドレス、MXなら「優先度 ホスト名」になる（R5春Ⅰ問2設問3(1)で出題）。

## 2. レコード早見表

| タイプ（RFC 1035）                                     | RDATA（中身）                                          | 用途                                                                    | 試験での着眼点/補足                                                                                                                                                                                                                                                                                |
| ------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A                                                 | IPv4アドレス                                           | 名前→IPv4                                                               | 複数登録で負荷分散。名前解決の終点                                                                                                                                                                                                                                                                         |
| AAAA                                              | IPv6アドレス                                           | 名前→IPv6                                                               | Aと同じ役割。IPv6は128ビット（IPv4の4倍）なのでA×4                                                                                                                                                                                                                                                         |
| <mark style="background: #FFB8EBA6;">CNAME</marc> | 別名の正規名                                             | 別名→正規名                                                                | CNAMEを置いた名前には他のレコードを置けない（MXやTXTもあると、どちらを答えるべきか矛盾するため）。そのため、SOAとNSが必ずあるゾーン頂点（example.jp そのもの）には置けない。キャンペーン終了後に外部サービスを解約してもCNAMEだけが残ると、第三者がそのサービスで同じ向き先を取得し、偽のページを出せてしまう<mark style="background: #FFB8EBA6;">「サブドメインテイクオーバー」</mark>の原因になる                                                   |
| <mark style="background: #FFB8EBA6;">NS</marc>    | 権威DNSサーバのホスト名                                      | 委任・権威サーバの指定                                                           | 「そのゾーンを担当する権威DNSサーバはどれか」を示すレコード。<br>自ゾーンの頂点に置くNS：そのゾーン自身の権威DNSサーバを示しす。委任をしていなくてもどのゾーンにも必ずある。<br>親ゾーンに置くNS：サブドメインを別のゾーンとして切り出し、その担当サーバを示す（委任）。委任先は外部のサーバに限らず、自社の別サーバでも構わない。親ゾーンと子ゾーンの両方に置く。<br><mark style="background: #FFB8EBA6;">サブドメインの利用をやめるときは、親ゾーン側のNSを削除する。NSの残存も乗っ取りの原因になる</mark> |
| <mark style="background: #FFB8EBA6;">SOA</marc>   | プライマリ名、管理者アドレス、SERIAL、各種タイマー                       | ゾーンの管理情報（ゾーンに1つ）                                                      | 権威DNSサーバは通常、原本を持つプライマリと、その写しを持つセカンダリの2台以上で運用する。プライマリでゾーンを更新したらSERIALを増やす。セカンダリは定期的にSERIALを確認し、手元の写しより大きければゾーン転送で取り直す。試験では<mark style="background: #FFB8EBA6;">「ゾーンを書き換えたのにSERIALを増やし忘れ、セカンダリが古い情報を返し続けた」</mark>という形で出題される。                                                                |
| <mark style="background: #FFB8EBA6;">MX</marc>    | 優先度＋メールサーバ名                                        | メールの受信サーバ                                                             | 値が小さいほど優先。同値は負荷分散。値はホスト名（IPアドレスは書けない）                                                                                                                                                                                                                                                     |
| TXT                                               | <mark style="background: #FFB8EBA6;">任意の文字列</marc> | <mark style="background: #FFB8EBA6;">SPF、DKIM、DMARC、</marc>ドメイン所有確認など | 先頭のタグ（v=spf1 など）で用途を区別。1文字列は255バイトまで                                                                                                                                                                                                                                                      |
| PTR                                               | ホスト名                                               | 逆引き（IP→名前）                                                            | 名前は 10.2.0.192.in-addr.arpa のように逆順。メール受信側の送信元チェックに使われる                                                                                                                                                                                                                                    |
| SRV                                               | 優先度、重み、ポート、ホスト名                                    | サービスの提供サーバとポート                                                        | 「このサービスはどのサーバの何番ポートで提供されているか」をDNSで探す。名前は \_サービス.\_プロトコル.ドメイン の形で示す                                                                                                                                                                                                                        |
| <mark style="background: #FFB8EBA6;">CAA</marc>   | 発行を許可するCA                                          | 証明書を発行してよいCAの指定                                                       | CAは発行前にCAAを確認する義務がある。<mark style="background: #FFB8EBA6;">自社が許可していないCAによる誤発行を防ぐ</mark>（攻撃者が別のCAで自社ドメインの証明書を取るのを防ぐ）。許可したCAでの不正取得やCA自体の不正には無力                                                                                                                                               |
| DNSKEY / RRSIG / DS                               | 公開鍵 / 署名 / 子ゾーン鍵のハッシュ                              | DNSSEC                                                                | 次の4章                                                                                                                                                                                                                                                                                      |

### 2.1 例（MX・CNAME・TXT）

```
example.jp.            IN MX    10 mx1.example.jp.
example.jp.            IN MX    20 mx2.example.jp.
campaign.example.jp.   IN CNAME lp.cdn-service.example.
example.jp.            IN TXT   "v=spf1 ip4:192.0.2.0/24 -all"
```

- 仕様で決まっている部分：タイプ名、MXの「優先度 ホスト名」の並びと「小さいほど優先」、TXTの値を「"」で囲む書き方、SPFの「v=spf1」「ip4:」「-all」（RFC 7208）。
- 任意の部分：各ホスト名、「10」「20」の具体値、アドレス範囲。

### 2.2 TXTレコードの代表的な使い道

<mark style="background: #FFB8EBA6;">TXTレコードは任意の文字列を置ける</mark>ため、外部のシステムに情報を公開する用途に使われる。
<mark style="background: #FFB8EBA6;">名前は仕様やサービス側の指定で決まっているもの</mark>がある。決まっている場合、読み取る側はその決まった名前で問い合わせるので、違う名前に置くと見つけてもらえない。
example.jpに関する問い合わせを例に取ると、名前を下記のような形式で記載しておく。

| 用途       | 名前をどの形式で記載しておくか（example.jp の場合）                          | 値の先頭          |
| -------- | -------------------------------------------------------- | ------------- |
| SPF      | example.jp（ドメインそのもの）                                     | v=spf1        |
| DKIM公開鍵  | セレクタ._domainkey.example.jp（例：sel1._domainkey.example.jp） | v=DKIM1       |
| DMARC    | _dmarc.example.jp                                        | v=DMARC1      |
| ドメイン所有確認 | example.jp など、サービス側が指定する名前                               | サービス側が指定する文字列 |

- 試験での着眼点：書く名前を間違えると認証されない（例：DMARCを \_dmarc.example.jp ではなく、SPFと同じ example.jp に書いてしまう）。DKIMのセレクタ（DKIM-Signatureのsタグ）は送信側が決める名前で、鍵ごとに変えられる（「04_メール」参照）。
- ドメイン所有確認：クラウドサービスが「指定の文字列をTXTに登録してください」と求め、登録できたことをドメイン管理者である証拠とする。

（仕様で決まっている部分：「\_domainkey」「\_dmarc」のラベル、「v=spf1」「v=DKIM1」「v=DMARC1」（RFC 7208、RFC 6376、RFC 7489））

## 3. 名前解決の流れ（www.example.jp を引く、かつキャッシュが空の場合）

1. 端末（スタブリゾルバ）→ フルサービスリゾルバ：再帰問合せ。
2. フルサービスリゾルバ → ルートサーバ：フルサービスリゾルバに「jp（トップレベルドメイン（TLD））のNS（権威DNSサーバ）はこれ」と委任情報が返る。
3. フルサービスリゾルバ→ jpの権威サーバ：「example.jpのNSはこれ」と返る。
4. フルサービスリゾルバ→ example.jpの権威サーバ：Aレコード（192.0.2.10）が返る。
5. フルサービスリゾルバはTTLの間キャッシュし、端末に返す。
※jpのNS：実際にはJPRSが運用する a.dns.jp などの複数台

## 4. DNSSEC（改ざん検知。暗号化ではない）

- <mark style="background: #FFB8EBA6;">DNSの応答（レコード）が、ゾーン管理者の登録した内容のまま改ざんされていないことを検証</mark>
- <mark style="background: #FFB8EBA6;">権威DNSサーバがレコードに署名（RRSIG）</mark>し、<mark style="background: #FFB8EBA6;">フルサービスリゾルバが公開鍵（DNSKEY）で検証</mark>する。
- <mark style="background: #FFB8EBA6;">親ゾーンに子ゾーンの鍵のハッシュ（DS）を置き、ルートから順に「信頼の連鎖」をたどる。</mark>
- 守れるもの：応答の改ざん・偽装（キャッシュポイズニング）。
- 守れないもの：通信の盗聴（中身は平文のまま）。盗聴対策はDoT／DoH。
- 検証するのはフルサービスリゾルバ。権威側だけ署名しても、リゾルバが検証しなければ効果がない。
- TLS1.3ハンドシェイク（R7春問3）のとの違い
	- <mark style="background: #FFB8EBA6;">DNSSECは「正しいIPアドレスを得たか」、TLSは「そのIPアドレスの先にいる相手が本物か」を確かめる。</mark>
	- TLS1.3ハンドシェイクは接続した相手が、その名前の正当なサーバであることを検証する。
	- DNSの応答を偽装されて偽サーバに誘導されても、偽サーバは正規の秘密鍵を持たないため、TLSの検証で失敗する。

| 役割          | DNSSEC          | TLS 1.3                                           |
| ----------- | --------------- | ------------------------------------------------- |
| 公開鍵を渡す      | DNSKEY          | Certificate（サーバ証明書と中間CA証明書のチェーン）                  |
| 上位がその鍵を保証する | 親ゾーンのDS（親が署名）   | CAによる証明書への署名                                      |
| 信頼の起点       | リゾルバが持つルートの鍵    | 端末が持つルートCA証明書                                     |
| その鍵による署名    | RRSIG（レコードへの署名） | CertificateVerify（サーバ証明書の秘密鍵による、それまでのハンドシェイクへの署名） |

## 6. <mark style="background: #FFB8EBA6;">攻撃と対策</marc>

| 攻撃                | 仕組み                                                                          | 対策（解答の型）                             |
| ----------------- | ---------------------------------------------------------------------------- | ------------------------------------ |
| DNSキャッシュポイズニング    | 正規の応答より先に偽の応答を送り込み、フルサービスリゾルバのキャッシュに偽のAレコードを覚えさせる。トランザクションIDと送信元ポートを当てる必要がある | 送信元ポートのランダム化、DNSSECの検証、外部からの再帰問合せの拒否 |
| サブドメインテイクオーバー     | 外部サービス解約後もCNAME（サブドメインを委任している場合はNS）が残り、その向き先を第三者が取得して自社ドメインのURLで偽コンテンツを出す    | 解約手順にDNSレコード削除を入れる、権威DNSのレコードの棚卸し    |
| DNSリフレクション（DRDoS） | 送信元IPを標的に偽装した小さな問合せで、大きな応答を標的に送らせる                                           | オープンリゾルバの解消（再帰問合せを社内からに限定）、応答レート制限   |
| ゾーン転送の悪用          | AXFRでゾーン全体を取得し、内部ホスト名などを調べる                                                  | ゾーン転送をセカンダリのIPアドレスに限定                |
| DNSトンネリング         | TXTなどの問合せ・応答にデータを埋め込み、C&C通信や持ち出しに使う                                          | 長いサブドメインや大量のTXT問合せの監視、外部DNSへの直接通信の禁止 |
| DNSリバインディング       | 名前解決のたびに別のIPを返し、ブラウザやサーバに内部アドレスへアクセスさせる。SSRF対策のすり抜けにも使われる                    | 宛先チェックを「名前解決後のIPアドレス」で行う、Hostヘッダの検証  |

## 7. 混同しやすいところ

- SNIとHost：どちらも接続先の名前。<mark style="background: #FFB8EBA6;">SNIはTLS（暗号化前に平文で送る）、HostはHTTP（TLSの内側）。</mark>DNSの話ではないが、CDNやドメインフロンティングの問題でDNSと一緒に出る（R4春Ⅱ問2）。
- CNAMEとNS：CNAMEは「この名前は別名」、NSは「この名前以下の管理は別サーバ」。どちらも残存すると乗っ取られる（R7春問4）。
- SPFレコードを置く名前：<mark style="background: #FFB8EBA6;">ヘッダFromではなくエンベロープFrom（Return-Path）のドメイン。DMARCはヘッダFromのドメイン。</mark>
