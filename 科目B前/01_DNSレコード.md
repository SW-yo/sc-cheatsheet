# DNSレコード あんちょこ

## 0. まず押さえる全体像

| 役割 | 何をするか | 試験での着眼点 |
|---|---|---|
| スタブリゾルバ | 端末（OS）内のDNSクライアント。フルサービスリゾルバに問い合わせるだけ | hostsファイル改ざん、端末のDNS設定変更 |
| フルサービスリゾルバ（キャッシュDNSサーバ） | 再帰問合せを受け、ルートから順に反復問合せして答えを集め、キャッシュする | キャッシュポイズニングの標的。外部からの再帰問合せを許すとオープンリゾルバ |
| 権威DNSサーバ（コンテンツサーバ） | 自ゾーンの正式な情報だけを答える | ゾーン転送の制限、ゾーンデータの改ざん、DNSSECの署名側 |

- ゾーン：1つの権威DNSサーバが責任をもつ名前の範囲。サブドメインを別サーバに任せることを委任という（NSレコードで行う）。
- 再帰問合せ：「最終的な答えをくれ」という問合せ（スタブ→フルサービスリゾルバ）。
- 反復問合せ：「知っている範囲で答えて」という問合せ（フルサービスリゾルバ→各権威サーバ）。
- TTL：キャッシュしてよい秒数。切替作業の前に短くしておくと、切替が早く反映される。

## 1. リソースレコードの書式

```
www.example.jp.   3600   IN   A   192.0.2.10
（名前）          （TTL） （クラス）（タイプ）（RDATA）
```

- 仕様で決まっている部分：「名前 TTL クラス タイプ RDATA」の並び、クラス「IN」、タイプ名（RFC 1035）。末尾の「.」は完全修飾（FQDN）の意味。
- 任意の部分：「www.example.jp」「3600」「192.0.2.10」（example.jp と 192.0.2.0/24 は説明用に予約された名前とアドレス）。

## 2. レコード早見表

| タイプ | RDATA（中身） | 用途 | 試験での着眼点 |
|---|---|---|---|
| A | IPv4アドレス | 名前→IPv4 | 複数登録で負荷分散。名前解決の終点 |
| AAAA | IPv6アドレス | 名前→IPv6 | Aと同じ役割。IPv6は128ビット（IPv4の4倍）なのでA×4 |
| CNAME | 別名の正規名 | 別名→正規名 | 同じ名前に他のレコードを置けない。ゾーン頂点（example.jp自体）に置けない。サブドメインテイクオーバーの原因 |
| NS | 権威DNSサーバのホスト名 | 委任・権威サーバの指定 | 親ゾーンと子ゾーンの両方に置く。NSの残存も乗っ取りの原因になる |
| SOA | プライマリ名、管理者アドレス、SERIAL、各種タイマー | ゾーンの管理情報（ゾーンに1つ） | SERIALの増加でセカンダリが更新を判断（ゾーン転送のきっかけ） |
| MX | 優先度＋メールサーバ名 | メールの受信サーバ | 値が小さいほど優先。同値は負荷分散。値はホスト名（IPアドレスは書けない） |
| TXT | 任意の文字列 | SPF、DKIM、DMARC、ドメイン所有確認など | 先頭のタグ（v=spf1 など）で用途を区別。1文字列は255バイトまで |
| PTR | ホスト名 | 逆引き（IP→名前） | 名前は 10.2.0.192.in-addr.arpa のように逆順。メール受信側の送信元チェックに使われる |
| SRV | 優先度、重み、ポート、ホスト名 | サービスの提供サーバとポート | 名前は _サービス._プロトコル.ドメイン の形 |
| CAA | 発行を許可するCA | 証明書を発行してよいCAの指定 | CAは発行前にCAAを確認する義務がある。誤発行対策 |
| DNSKEY / RRSIG / DS | 公開鍵 / 署名 / 子ゾーン鍵のハッシュ | DNSSEC | 次の4章 |

### 2.1 例（MX・CNAME・TXT）

```
example.jp.            IN MX    10 mx1.example.jp.
example.jp.            IN MX    20 mx2.example.jp.
campaign.example.jp.   IN CNAME lp.cdn-service.example.
example.jp.            IN TXT   "v=spf1 ip4:192.0.2.0/24 -all"
```

- 仕様で決まっている部分：タイプ名、MXの「優先度 ホスト名」の並びと「小さいほど優先」、TXTの値を「"」で囲む書き方、SPFの「v=spf1」「ip4:」「-all」（RFC 7208）。
- 任意の部分：各ホスト名、「10」「20」の具体値、アドレス範囲。

### 2.2 TXTレコードの代表的な使い道（登録する名前まで覚える）

「登録する名前」は、レコード行の左端に書く名前（所有者名）のこと。受信側などはこの名前を指定してDNSに問い合わせるので、名前が違うと見つけてもらえない。

| 用途 | 登録する名前 | 値の先頭 |
|---|---|---|
| SPF | ドメインそのもの（エンベロープFromのドメイン） | v=spf1 |
| DKIM公開鍵 | セレクタ._domainkey.ドメイン | v=DKIM1 |
| DMARC | _dmarc.ドメイン（ヘッダFromのドメイン） | v=DMARC1 |

- 仕様で決まっている部分：「_domainkey」「_dmarc」というラベル名、各「v=」の値。
- 任意の部分：セレクタ名（DKIM-Signatureの s= で送信側が決める）。

## 3. 名前解決の流れ（www.example.jp を引く場合）

1. 端末（スタブリゾルバ）→ フルサービスリゾルバ：再帰問合せ。
2. フルサービスリゾルバ → ルートサーバ：「jpのNSはこれ」と委任情報が返る。
3. → jpの権威サーバ：「example.jpのNSはこれ」と返る。
4. → example.jpの権威サーバ：Aレコード（192.0.2.10）が返る。
5. フルサービスリゾルバはTTLの間キャッシュし、端末に返す。

## 4. DNSSEC（改ざん検知。暗号化ではない）

- 権威DNSサーバがレコードに署名（RRSIG）し、フルサービスリゾルバが公開鍵（DNSKEY）で検証する。
- 親ゾーンに子ゾーンの鍵のハッシュ（DS）を置き、ルートから順に「信頼の連鎖」をたどる。
- 守れるもの：応答の改ざん・偽装（キャッシュポイズニング）。
- 守れないもの：通信の盗聴（中身は平文のまま）。盗聴対策はDoT／DoH。
- 検証するのはフルサービスリゾルバ。権威側だけ署名しても、リゾルバが検証しなければ効果がない。

## 5. 通信方式とポート

| 方式 | トランスポート | ポート | 試験での着眼点 |
|---|---|---|---|
| 通常のDNS | UDP（大きい応答やゾーン転送はTCP） | 53 | FWでTCP/53を塞ぐとゾーン転送や大きい応答が失敗する |
| DoT（DNS over TLS） | TCP＋TLS | 853 | 専用ポートなので管理者が識別・遮断しやすい |
| DoH（DNS over HTTPS） | TCP＋TLS＋HTTP | 443 | Webと見分けにくく、社内のDNS監視・フィルタをすり抜ける |

## 6. 攻撃と対策（設問で問われる形）

| 攻撃 | 仕組み | 対策（解答の型） |
|---|---|---|
| キャッシュポイズニング | 正規の応答より先に偽の応答を送り込み、フルサービスリゾルバのキャッシュに偽のAレコードを覚えさせる。トランザクションIDと送信元ポートを当てる必要がある | 送信元ポートのランダム化、DNSSECの検証、外部からの再帰問合せの拒否 |
| サブドメインテイクオーバー | 外部サービス解約後もCNAME（またはNS）が残り、その向き先を第三者が取得して自社ドメインのURLで偽コンテンツを出す | 解約手順にDNSレコード削除を入れる、権威DNSのレコードの棚卸し |
| DNSリフレクション（DRDoS） | 送信元IPを標的に偽装した小さな問合せで、大きな応答を標的に送らせる | オープンリゾルバの解消（再帰問合せを社内からに限定）、応答レート制限 |
| ゾーン転送の悪用 | AXFRでゾーン全体を取得し、内部ホスト名などを調べる | ゾーン転送をセカンダリのIPアドレスに限定 |
| DNSトンネリング | TXTなどの問合せ・応答にデータを埋め込み、C&C通信や持ち出しに使う | 長いサブドメインや大量のTXT問合せの監視、外部DNSへの直接通信の禁止 |
| DNSリバインディング | 名前解決のたびに別のIPを返し、ブラウザやサーバに内部アドレスへアクセスさせる。SSRF対策のすり抜けにも使われる | 宛先チェックを「名前解決後のIPアドレス」で行う、Hostヘッダの検証 |

## 7. 混同しやすいところ

- SNIとHost：どちらも接続先の名前。SNIはTLS（暗号化前に平文で送る）、HostはHTTP（TLSの内側）。DNSの話ではないが、CDNやドメインフロンティングの問題でDNSと一緒に出る。
- CNAMEとNS：CNAMEは「この名前は別名」、NSは「この名前以下の管理は別サーバ」。どちらも残存すると乗っ取られる。
- SPFレコードを置く名前：ヘッダFromではなくエンベロープFrom（Return-Path）のドメイン。DMARCはヘッダFromのドメイン。
