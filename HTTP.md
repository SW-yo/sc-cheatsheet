### 1. 基本構成
#### (1) 流れ
「**リクエスト**」と「**レスポンス**」
①**クライアントがリクエスト**を送る。
②**サーバーがレスポンス**を返す。

#### (2) 構成
「**リクエスト/ステータスライン**」と「**HTTPヘッダ**」と「**HTTPボディ**」

### 2. リクエスト/ステータスライン
#### (1) リクエストライン
  - 構造 : メソッド␣リクエストターゲット␣HTTPバージョン 
    例）GET /products/list.html HTTP/1.1
#### (2) ステータスライン
  - HTTPバージョン␣ステータスコード␣理由フレーズ 
    例）HTTP/1.1 404 Not Found
#### (3) メソッド

| メソッド    | 概要                       | サーバー書き換え無し（読むだけ） | 冪等（何回でも1回と同じ） | 試験での着眼点                                                                                                                                                                                                                                                                                           |
| ------- | ------------------------ | ---------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET     | リソースの取得                  | ○                | ○             | 狙われ方：クエリ文字列がアクセスログ・ブラウザ履歴・Refererヘッダーに残り、URLに埋め込んだセッションIDや個人情報が外部サイトへ漏えいする。更新処理をGETで受け付けていると、imgタグやリンクを踏ませるだけでCSRFが成立する。SameSite=Laxでも、他サイトからのトップレベル遷移（リンクのクリック）ではCookieが送信される。対策：機密情報はURLに含めずPOSTのボディで送る、Referrer-Policyを設定する、更新処理はGETで受け付けない                                                    |
| HEAD    | GETと同じ応答のヘッダー部のみ取得       | ○                | ○             | 狙われ方：アクセス制御をGET・POSTだけに設定していると、HEADなど別メソッドで制御をすり抜けられる（メソッド改ざんによる回避）。ボディなしでリソースの存在や更新日時を調べられ、事前調査に使われる。対策：許可するメソッドを列挙し、それ以外を拒否する                                                                                                                                                                   |
| POST    | データの送信・処理                | ×                | ×             | 狙われ方：CSRFの主な攻撃対象。Content-Typeがapplication/x-www-form-urlencoded、multipart/form-data、text/plainのいずれかであれば「単純リクエスト」となりプリフライトが発生しないため、他サイトのフォームから送信できる。JSONを受けるAPIでも、Content-Typeを検証していないとtext/plainで送られて処理される。対策：推測困難でセッションに紐づくCSRFトークン、CookieへのSameSite属性付与、OriginヘッダーまたはRefererヘッダーの検証、重要な操作の前の再認証 |
| PUT     | 指定URLへのリソースの作成・置換        | ×                | ○             | 狙われ方：WebDAVなどで不要なのに有効だと、Webシェルなど任意のファイルを公開ディレクトリに設置される。クロスオリジンのPUTはプリフライトの対象になるため、CORS応答のAccess-Control-Allow-Methodsに含めてよいかが問われる。対策：不要なら無効化し、必要なら認証・認可をかける                                                                                                                                       |
| DELETE  | 指定リソースの削除                | ×                | ○             | 狙われ方：リソースIDを書き換えるだけで他人のデータを削除できる（オブジェクト単位の認可不備、IDOR）。対策：リクエストした利用者がそのリソースの所有者かをサーバー側で毎回確認する                                                                                                                                                                                                       |
| PATCH   | リソースの部分更新                | ×                | ×             | 狙われ方：送られた項目をそのまま反映する実装だと、role・is_adminなど本来変更できない項目まで書き換えられる（マスアサインメント）。DELETEと同じくIDORも狙われる。対策：更新を許可する項目を許可リストで限定し、オブジェクト単位で認可する                                                                                                                                                                   |
| OPTIONS | 利用可能な通信オプションの問い合わせ       | ○                | ○             | 狙われ方：CORSのプリフライトで使われる。リクエストのOriginをそのままAccess-Control-Allow-Originに反射し、Access-Control-Allow-Credentials: trueを返す設定不備があると、他サイトから利用者のCookie付きでデータを読み取られる。応答のAllowヘッダーから有効なメソッドが判明する。対策：許可するオリジンを固定のリストと照合して返す                                                                                       |
| TRACE   | 受信したリクエストをそのまま返す（ループバック） | ○                | ○             | 狙われ方：XST（クロスサイトトレーシング）。応答にCookieヘッダーやAuthorizationヘッダーがそのまま含まれるため、HttpOnly属性を付けたCookieでもスクリプトから読まれ得る。現行ブラウザはfetchやXMLHttpRequestからのTRACE送信を禁止しているが、試験の解答としてはサーバー側での無効化が定石。対策：Webサーバーの設定でTRACEを無効化する                                                                                               |
| CONNECT | プロキシにトンネル（主にHTTPS）を確立させる | ×                | ×             | 狙われ方：接続先のホスト・ポートを制限しないと、外部から内部ネットワークへの侵入経路にされたり、25番ポートへのトンネルでスパムメール送信の踏み台（オープンプロキシ）にされたりする。対策：プロキシ利用者を認証し、CONNECTの接続先ポートを443などに限定する                                                                                                                                                               |

- 仕様で決まっている部分：安全・冪等の区分（RFC 9110、PATCHはRFC 5789）、単純リクエストとプリフライトの条件、Allow-Origin: * とCredentials: true は併用できないこと（Fetch Standard）、SameSite=Laxではトップレベル遷移のGETでCookieが送られること（RFC 6265bis）
- 製品・実装に依存する部分：SameSite属性を指定しないCookieをLaxとして扱う挙動（Chromeなどのブラウザの実装）、TRACEを無効化する設定名（Apacheの場合はTraceEnable Off）、WebDAVの有無
- 説明用に作った部分：表中のrole・is_adminは説明のための項目名
### 3. HTTPヘッダ（HTTP/1.1、RFC 9110／9112）
#### (1) 構造
- 1行が「フィールド名: 値」の形式で、行末はCRLF。
- ヘッダー部の終わりは空行（CRLFのみの行）で示され、その後にボディが続く。
- 「Set-Cookie」以外は同名ヘッダーが複数ある場合はカンマ区切りで1行に結合できる。
  例）
```
POST /login HTTP/1.1　←リクエストライン
Host: www.example.com　←以下、空行までヘッダ
Content-Type: application/x-www-form-urlencoded
Content-Length: 26
Cookie: SESSIONID=abc123

userid=taro&password=xxxxx　←ボディ
```

```
HTTP/1.1 302 Found　←リクエストライン
Location: https://www.example.com/mypage
Set-Cookie: SESSIONID=def456; Secure; HttpOnly; SameSite=Lax
```

#### (2) 主要ヘッダ一覧
| ヘッダー                               | 方向  | 概要                                                                                                                                                                                                       | 試験での着眼点                                                                                                 |
| ---------------------------------- | --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 🖥️**Host**                        | 要求  | 接続先のホスト名（とポート）                                                                                                                                                                                           | HTTP/1.1で必須。Hostヘッダーインジェクション、仮想ホストの振り分け                                                                 |
| 🖥️**Cookie**                      | 要求  | 保存済みCookieをサーバーへ送る。セッションIDを含むことが多い                                                                                                                                                                       | セッションIDの漏えい・盗用                                                                                          |
| ⚙️**Set-Cookie**                   | 応答  | Cookieの保存を指示                                                                                                                                                                                             | Secure／HttpOnly／SameSite／Domain／Path属性の意味と効果                                                            |
| Authorization                      | 要求  | 認証情報（Basic、Bearerトークンなど）                                                                                                                                                                                 | Basicは平文相当（Base64）なのでTLS必須                                                                              |
| WWW-Authenticate                   | 応答  | 401応答で認証方式を提示                                                                                                                                                                                            | Authorizationとの対応関係                                                                                     |
| Location                           | 応答  | リダイレクト先（3xx）や作成先URL                                                                                                                                                                                      | オープンリダイレクト                                                                                              |
| 🖥️Origin                          | 要求  | リクエスト元のスキーム・ホスト（ドメイン）・ポート                                                                                                                                                                                | CORS判定、CSRF対策での検証                                                                                       |
| 🖥️**Referer**                     | 要求  | 遷移元のURL（同一ドメイン内）もしくはスキーム・ホスト（ドメイン）・ポート（Web標準ポート以外）                                                                                                                                                       | URL内のトークン漏えい、CSRF対策での検証                                                                                 |
| Content-Type                       | 双方  | ボディのメディアタイプと文字コード                                                                                                                                                                                        | MIMEスニッフィング、XSSとの関係                                                                                     |
| Content-Length                     | 双方  | ボディのバイト数                                                                                                                                                                                                 | Transfer-Encodingとの不整合によるリクエストスマグリング                                                                    |
| ⚙️**Cache-Control**                | 双方  | キャッシュの可否・期限<br>- no-cache : キャッシュは保存可だが、利用時にサーバに変更の有無を確認する<br>- no-store : キャッシュ禁止 <br>- private : Webブラウザ内などプライベートキャッシュのみ保存可<br>- public : 共有キャッシュにも保存可<br>- max-age : キャッシュの有効時間を秒単位で指定                | 個人情報を含む応答に「**no-store**」                                                                                |
| ⚙️Access-Control-Allow-Origin      | 応答  | クロスオリジンでの読み取りを許可するオリジン                                                                                                                                                                                   | 「*」や要求Originをそのまま返す設定の危険性                                                                               |
| ⚙️Access-Control-Allow-Credentials | 応答  | Cookie付きクロスオリジン要求の許可                                                                                                                                                                                     | 「*」とは併用不可                                                                                               |

**CORS** : Cross-Origin Resource Sharing、オリジン間リソース共有  
あるオリジンのWebページから、別のオリジンのリソースへアクセスすることを、サーバ側が許可する仕組み。
#### (3) Set-Cookie属性
- 意味 : 「ブラウザが今後どのリクエストにそのCookieを付けるか」の条件をサーバーが指定する。「送る」とはブラウザがリクエストの「Cookie」ヘッダーにそのCookieを載せることを指す。
- 例
```
Set-Cookie: SESSIONID=def456; Path=/; Secure; HttpOnly; SameSite=Lax
```
- cookieの設定

| 属性            | 概要                                         | 指定例                                   | 試験上のポイント                                                                                     |
| ------------- | ------------------------------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Secure**    | HTTPS通信のときだけcookieを送信する                    | Secure                                | 平文HTTPでの盗聴によるcookie漏えいを防ぐ                                                                    |
| **HttpOnly**  | JavaScript（document.cookie）からcookieを読めなくする | HttpOnly                              | XSSによるセッションIDの窃取を緩和する。XSS自体は防げない                                                             |
| **SameSite**  | 別サイトからのリクエストにcookieを付けるかを制御する              | SameSite=Strict / Lax / None          | CSRF対策。Strictは別サイトからは常に送らない、Laxはトップレベルの遷移（GETのリンク等）のみ送る、Noneは常に送る（Secure必須）。主要ブラウザは未指定時Lax扱い |
| **Domain**    | cookieを送信するドメインを指定する                       | Domain=example.com                    | 省略すると発行したホストのみに送られる。指定するとサブドメインにも送られ、範囲が広がる                                                  |
| **Path**      | cookieを送信するURLのパスを指定する                     | Path=/app                             | 指定パス配下にのみ送信。セキュリティ上の境界にはならない                                                                 |
| **Expires**   | cookieの有効期限を日時で指定する                        | Expires=Wed, 21 Oct 2026 07:28:00 GMT | Expires・Max-Ageとも省略するとブラウザ終了で消えるセッションcookieになる                                               |
| Max-Age       | cookieの有効期間を秒数で指定する                        | Max-Age=3600                          | Expiresと両方あればMax-Ageが優先。0以下で即削除                                                              |
| __Secure- 接頭辞 | 名前の先頭に付けると、Secure属性付きかつHTTPSからの設定のみ受け付ける   | __Secure-sid=...                      | cookie名で安全な設定を強制する                                                                           |
| __Host- 接頭辞   | Secure必須、Domain指定禁止、Path=/ 必須の条件でのみ受け付ける   | __Host-sid=...                        | サブドメインからのcookie上書き（セッション固定攻撃など）を防ぐ                                                           |
- 流れ
①サーバー → ブラウザ（レスポンス）
```
Set-Cookie: SESSIONID=def456; Path=/; Secure; HttpOnly; SameSite=Lax
```
②ブラウザが Cookie と属性を保存
③ ブラウザ → サーバー（以後のリクエスト）
```
GET /mypage HTTP/1.1
Host: www.example.com
Cookie: SESSIONID=def456
```

#### (4) Refererヘッダー
Refererはブラウザーが次のサイトにアクセスする際、自分から最初の一言として「ここのページから来た」と相手のサーバーへ自主的に提示する情報。
ただし元のサイト側が指定する `Referrer-Policy`（レスポンスヘッダーやHTMLのmeta要素）によってブラウザが `Referer` ヘッダーにどこまでの情報を送信するかを制御できる。
主な設定値と送られる値の範囲：
- `no-referrer` : ヘッダー自体を一切送信しない。
- `origin` : パスやクエリを除き、オリジン（スキーム＋ドメイン＋ポート）のみを送信する。
- `same-origin` : 同一オリジン内の遷移にのみ完全なURLを送信し、外部サイトへは送信しない。
- `strict-origin-when-cross-origin`（多くのブラウザの既定値） : 同一オリジンには完全なURL、異なるオリジン（外部）にはオリジンのみを送信し、HTTPSからHTTPへの安全性が下がる遷移（ダウングレード）の時は送信しない。
- `unsafe-url` : クロスオリジンやHTTPS→HTTPの制限に関わらず、常に完全なURLを送信する。
